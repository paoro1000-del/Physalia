# カナリア接触ログの記録と手動確認

このガイドは、管理権限のある環境でカナリアURLやデコイ配信への接触を記録し、担当者が既存のWebサーバー／ログ基盤で確認するための考え方です。Physaliaには、利用者の既存ログを取り込んで自動判定する機能はありません。ログ分析画面、取込API、判定スクリプト、検知ルールは提供しません。Infinite Streamサンプル自身が出す運用イベントは標準出力へ記録されます。

## 何を記録するか

まず、調査に必要な最小限のメタデータに絞ります。

| 項目 | 用途 | 注意点 |
| --- | --- | --- |
| `time` | 接触の時系列 | UTCまたはタイムゾーン付き時刻に統一し、時刻同期する |
| `event` | 記録の種類 | 例：`decoy_contact` |
| `decoy_id` | どのデコイに対する要求か | URLや秘密トークンそのものを記録せず、管理者台帳の不透明なIDを使う |
| `request_id` | 同じ要求を配信ログ内で照合 | サーバー側で生成するランダムなID。利用者の身元を示さない |
| `method`, `status` | 要求方法とサーバー応答 | 応答コードだけでファイルの取得完了は断定できない |
| `bytes_sent`, `request_seconds` | サーバーが処理した応答量と時間 | クライアントが全内容を受け取った証明ではない |
| `source_ip` | 必要な場合の自社ログ内相関 | 個人に結び付く可能性がある情報として扱い、必要性・閲覧者・保存期間を定める。不要なら記録しない |
| `user_agent` | 自動取得・クライアント種別の手掛かり | 偽装でき、人物特定や攻撃者断定には使えない。必要性がなければ記録しない |

**記録しないもの：** パスワード、Cookie、Authorizationヘッダー、リクエスト本文、顧客データ、完全なカナリアURL、URLのクエリ文字列・フラグメント。カナリアURLの秘密トークンを含み得るため、一般的な生アクセスログをそのまま共有・転送しないでください。既存のWebサーバーや監視サービスで、URLを不透明な`decoy_id`に対応づける方法を選びます。マッピング台帳はログと分け、管理者だけがアクセスできる場所に保管します。

## JSON Linesの記録例

以下は架空データです。`192.0.2.0/24`は文書用の予約アドレス帯です。`source_ip`は必要性がある場合だけ追加します。

```jsonl
{"time":"2026-10-20T01:12:04Z","event":"decoy_contact","decoy_id":"cfg-backup-01","request_id":"req-7a31","method":"GET","status":200,"bytes_sent":894,"request_seconds":0.018}
{"time":"2026-10-20T01:13:19Z","event":"decoy_contact","decoy_id":"cfg-backup-01","request_id":"req-7a32","method":"HEAD","status":200,"bytes_sent":0,"request_seconds":0.006,"source_ip":"192.0.2.44"}
```

ログ形式を自社で決める場合も、トークンではなくランダムな`decoy_id`を残す考え方を使えます。たとえばNginxなら、`$uri`からクエリを含まないパスを識別子へ対応づけ、ログ出力には対応IDだけを含めます。実際の秘密パスを設定例やGit管理ファイルに書かないでください。プロキシ配下の送信元IPは、信頼したプロキシが設定した値だけを使い、任意の`X-Forwarded-For`を信用しません。

付属する`examples/nginx-decoy.conf`は、時刻・イベント・固定のデコイID・要求ID・メソッド・応答状態・送信量・処理時間をJSON形式で記録する設定例です。パスと送信元IPは出力しません。別のデコイを監視する場合はIDを分け、ログファイル自体の閲覧者と保存期間を設定してください。

## 手動で確認する流れ

1. **正規の自動アクセスを確認する。** メール保護スキャナー、リンクプレビュー、社内監視、バックアップ処理がURLを取得していないか、導入時刻や管理記録と照らします。
2. **時刻順に並べる。** `decoy_id`ごとにGET/HEAD等の順序、応答コード、要求間隔、サーバー側の送信量を確認します。繰り返しアクセスや通常と違う系列は調査候補です。
3. **自社の関連ログだけを照合する。** 必要な場合に限り、同じ`request_id`や時間帯を、自組織が管理するWebサーバー・認証基盤のログで担当者が確認します。別組織のシステムにログインしたり、送信元へ接続して調べたりしません。
4. **根拠と不確実性を記録する。** 「URL要求を受けた」「サーバーが応答した」と「人がファイルを読んだ」「内容を保存した」「侵害した」は別の事実です。HTTP 200や送信バイト数だけで取得完了・攻撃者の身元・侵害を断定しません。
5. **必要な記録を保全し、担当者へ連絡する。** 原本をアクセス制限されたログ基盤に残し、時刻・タイムゾーン・確認者・判断理由を記録します。通常利用者や自動スキャナーの誤検知も調べてから、既存のインシデント対応手順に従います。

## 個人情報・法令への配慮（日本）

IPアドレス、利用者ID、User-Agent等は、他の情報と照合して個人を識別できる場合があります。目的を防御・インシデント対応に限定し、収集項目、アクセス権限、保管場所、保存期間、削除手順を決めてください。閲覧者を限定し、ログの改ざん・漏えいを防ぎます。通信内容や認証秘密を収集しないでください。ログを外部サービスへ送る場合は、送信先、委託・第三者提供、契約、国外移転の有無を別途確認します。

個人情報保護委員会のガイドラインは、個人データを扱うシステムに関する技術的安全管理措置の例として、アクセス制御、不正アクセス防止、ログ等の定期分析を挙げています。一方、個別ログが個人情報に当たるか、通知・利用目的・保存期間等に何が必要かは、ログ内容と事業の実態によります。これは一般的な運用上の説明で、個別案件の適法性を保証しません。[個人情報保護委員会：個人情報保護法ガイドライン（通則編）](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/) / [ログファイルの管理に関するQ&A](https://www.ppc.go.jp/all_faq_index/faq4-q802/)

**やってはいけないこと：** 送信元端末への侵入・ポートスキャン・マルウェア配布・無断追跡、第三者のアカウントやシステムへのログイン、取得した情報の公開や脅迫、必要性のない個人データの過剰収集。デコイへのアクセスがあったことは、相手に対する反撃や別システムへのアクセス権限を与えません。
