## Baseline defenses remain necessary

Deception detects or delays some post-entry activity; it does not prevent initial access, replace authorization checks, or contain an incident by itself. Keep internet-facing systems and VPN appliances inventoried and patched, use MFA for privileged accounts, limit repeated login attempts, retain and review authentication and access logs, restrict lateral access between systems, and maintain recoverable backups. Add decoys alongside these controls and connect their alerts to an owner who can respond. Do not wait for a decoy alert before containing a confirmed compromise. The Personal Information Protection Commission's October 2026 warning describes incidents involving unpatched vulnerabilities, weak authentication, delayed detection, excessive cross-system access and API weaknesses, and calls for layered security measures. [PPC warning, revised October 7, 2026](https://www.ppc.go.jp/files/pdf/261007_warning.pdf) (Japanese).

This is a practical starting order for small teams, not a claim that every organization has the same legal duties or risk profile. Prioritize systems that process personal data and internet-facing identity infrastructure, assign an owner for patching and alert review, then deploy a small number of monitored decoys in an isolated path.

### Inventory public files and discovery endpoints

AI-assisted reconnaissance can begin by downloading JavaScript bundles, source maps, runtime configuration, and API descriptions, then probing the routes they reveal. Wiz reported this sequence in its October 2026 observations of ARTEX-related activity; Microsoft separately reported rapid scanning, password spraying, and OAuth application abuse. This is a reason to reduce exposed information and shorten detection time, not evidence that every crawler will follow the same sequence. [Wiz research](https://www.wiz.io/blog/artex-in-the-wild-storm-0940-expands-targeting-of-it-and-software-vendors) [Microsoft investigation](https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/)

For each public hostname, including staging and forgotten subdomains:

1. Inventory reachable applications, directories, API routes and cloud identity integrations. Review the site from outside the hosting network using only authorized accounts and destinations.
2. Confirm that real `.env` files, `.git` metadata, database files, backups, editor files and deployment archives cannot be downloaded. Check response bodies as well as status codes: a single-page-app fallback can return its normal HTML with status `200` for a nonexistent path.
3. Do not publish production source maps unless there is a reviewed need. If support requires them, restrict access and keep them out of public build directories. Remove debug routes and protect API descriptions such as Swagger/OpenAPI with the same access controls as the API when they are not intended for public use.
4. Keep access logs and alert on bursts that touch many distinct paths, source-map or API-description paths, repeated authentication or recovery attempts, and unusual `404` sequences followed by successful responses. Combine signals across accounts and time; a single IP address or user-agent is easy to rotate and is not a reliable allow/deny rule.
5. Keep unknown-path behavior ordinary and consistent. Do not route every missing path to a decoy page; that can expose a fingerprint and can hide real routing mistakes. Place decoys on a small number of plausible, monitored paths after the real exposure review.

The included decoy generators do not scan your production host or verify its public files. Treat this checklist as an operator-run review, and repeat it after deployments or domain changes.

For Nginx sites, the integration kit includes `examples/nginx-recon-log.conf` and `examples/review_http_recon.py`. Enable the log format only on public application routes you own, protect the raw log (it contains client IPs, host names and paths), then run `python examples/review_http_recon.py --input adg-recon.jsonl`. The local report flags a single request to a sensitive-path category or at least 12 distinct 404 paths from one source within five minutes. It also flags a candidate when such an enumeration is followed within the same five-minute window by a 2xx or 3xx response. This can identify a reached route, but redirects, CDN behavior and single-page-app fallbacks can create false positives; review the referenced raw log lines and application behavior. Events are grouped by host and client address so requests to different virtual hosts are not combined; older logs without a `host` field are still accepted and grouped under an empty host for single-source rules. A separate distributed-enumeration candidate combines 404 paths across addresses only when a nonempty host is present: at least 20 distinct paths and 3 source addresses within five minutes. The report contains counts, a per-run pseudonymous `host_id` and input line numbers, not the host, IPs or paths. Several unrelated scanners or normal users on one busy site can meet this threshold; it is a triage signal, not proof of one coordinated actor. If Nginx is behind a proxy, configure its real-IP handling only for explicitly trusted proxy addresses; do not trust arbitrary client-supplied `X-Forwarded-For`. Path categorization applies up to eight percent-decoding passes, treats backslashes as separators, treats a decoded NUL as a possible path truncation boundary, checks semicolon path parameters and trailing dots or spaces as possible aliases, applies Unicode NFKC normalization, and removes invisible format characters to catch common obfuscated variants. The eight-pass cap bounds work; deeper encodings may remain unclassified. These transformations are only classification heuristics: application and proxy normalization can differ, so confirm the actual route in the protected logs. Categories include environment and runtime config (including appsettings, application.properties, web.config, and common secret files), VCS or private metadata (including common cloud/container credential paths and Terraform state files), source maps, API descriptions, database or backup files, and debug/metrics endpoints. The path list is heuristic and not exhaustive; ordinary public files can also match. It prints category, status, time and source-log line references, but no raw path or IP; its source identifier is random per run. The thresholds are starting points, not a verdict or a block rule. Review the referenced lines in the protected log. The scan is limited to 250,000 valid records, 500,000 input lines (twice the record limit), 16 KiB per line and 1 GiB of input by default. Longer lines are skipped and counted as `oversized_record`. Lowering `--max-records` also lowers the line limit to twice that value. The report keeps the latest 10,000 findings in time order; if `findings_truncated` is true, split the log into smaller time ranges and review every part. Larger input files must also be split. Try the bundled synthetic example with `python examples/review_http_recon.py --input examples/recon-access-sample.jsonl`. The analyzer drops any query string or fragment in supplied uri values before classification and route hashing, so query values do not inflate route counts. The original log can still contain sensitive query data if it was recorded.

The JSON summary includes `records_skipped` and `skip_reasons` for malformed JSON, oversized lines and invalid event fields. Review these counts before relying on the findings; skipped records were not analyzed. The tool reports aggregate counts only and does not echo rejected log contents.

Authentication and recovery checks are also heuristic: 10 failed requests to a recognized sign-in route from one source, or 6 requests to a recognized recovery route, trigger a review candidate within five minutes. Across a known host, 25 failed sign-in requests or 15 recovery requests from at least 3 sources produce a distributed candidate. Sign-in failures count HTTP 400, 401, 403, 404 and 429; recovery routes count any status. Route names are matched heuristically, so ordinary users, health checks or unrelated APIs can match. The report includes counts, status and method distributions, pseudonymous IDs and line numbers; it does not identify accounts, prove an attack or confirm successful access. Do not use these candidates for automatic blocking. Common matched names include login/sign-in, OAuth/SSO, authorize/callback/token, and forgot/reset/password-recovery routes; custom route names may be missed.

Applications that return HTTP 200 for failed sign-ins will not match the status-based failure rule. Review their application or identity-provider authentication and audit logs.


The HTTP reconnaissance classifier also recognizes common environment-file names with stacked suffixes, such as `.env.production.local`. Sensitive-path categories include `.azure`, `.config/gcloud`, `.config/gh`, `.config/containers` and `.git-credentials`. This remains a path-name heuristic; confirm actual file delivery from the source logs and response behavior.

## Additional controls for organizations using AI agents

Decoys do not restrict the identities, tool permissions or host permissions available to an AI agent. OWASP's 2026 Q3 roundup describes an MCP distribution campaign that attempted to change tool definitions after approval and steer agents toward local credentials; no compromise was confirmed. A separate Q2 roundup describes researcher-controlled validation in which crafted error telemetry influenced coding-agent execution. These reports do not mean every agent is vulnerable, but approval-time review alone may not be enough. [OWASP 2026 Q3 roundup](https://genai.owasp.org/2026/10/08/genai-and-agentic-ai-exploit-roundup-q3-2026/) [OWASP 2026 Q2 roundup](https://genai.owasp.org/2026/07/08/genai-and-agentic-ai-exploit-roundup-q2-2026/) [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/?lang=us)

Do not assume an AI-assisted attacker will stop when a person would become tired. Microsoft reported multiple cases reaching privileged cloud access in under three hours, while Wiz reported some ARTEX-related sessions lasting 24–30 hours and adapting when blocked. These are observations from specific investigations, not a universal attacker profile. Plan for both fast access to persistence and sustained follow-on work: a decoy delay matters only if monitoring and response interrupt useful data access or persistence first. [Microsoft investigation](https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/) [Wiz research](https://www.wiz.io/blog/artex-in-the-wild-storm-0940-expands-targeting-of-it-and-software-vendors)

For a small organization, apply these controls through existing identity, endpoint and audit systems:

1. **Give each agent a distinct identity and least privilege.** Avoid shared high-privilege accounts and long-lived administrator tokens. Use short-lived credentials scoped to the required resources and actions. Do not give a read-only task write, send or delete permissions.
2. **Govern MCP servers and tool-definition changes.** Record approved publishers, versions, tool names and argument schemas. Review diffs and require re-approval on updates. `examples/agent-tool-approval-template.json` in the integration-samples ZIP is a record template. If recording a schema digest, hash the exact approved schema file with SHA-256 and compare against that same file. The template does not retrieve or monitor tool definitions or enforce an allowlist. Remove unused MCP integrations and deny agent access to credential stores, SSH keys and cloud configuration by default.
3. **Isolate execution.** Restrict repositories, shells, filesystems and network access per task. Treat model-generated paths, commands, URLs and search filters as untrusted; validate them against allowlists in host-side code. Do not expose secrets through environment variables or working directories unnecessarily, and limit outbound destinations.
4. **Require independent approval for high-impact actions.** Do not let model judgment alone send email, publish externally, release code, grant permissions, change credentials, delete data or make payments. Enforce human review or a separate policy check in the tool implementation.
5. **Trace and stop execution.** Correlate agent identity, caller, tool and version, target resource, result, child processes and outbound connections in existing logs. Prepare stop and token-revocation procedures. A decoy contact is an investigation signal; it does not prove an agent's execution history or a compromise.

This tool's cloud-log screen is a local review aid for exported Entra and related logs. It does not monitor MCP definitions, isolate endpoints, approve tool execution or revoke credentials automatically. See [Reviewing identity and cloud logs](#reviewing-identity-and-cloud-logs) for its actual coverage and log requirements.

## Smallest useful deployment

### Canary provider logs and privacy

When a canary URL is requested, its provider and hosting operator may receive request metadata such as the source IP address, time and User-Agent. Check the provider's actual collection, retention and storage-region terms. Requests may come through a VPN, relay or crawler, so treat an IP address as an investigation clue rather than proof of the attacker's identity. Review the provider's privacy notice, log access and deletion controls, subprocessors and storage regions. Do not put customer IDs or other identifying data in the URL; align log purpose, retention and access with your internal policy. The Personal Information Protection Commission explains that device identifiers may be personal-related information even when they do not identify an individual by themselves. The legal treatment depends on how the information is combined and used; see the [General Guidelines](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/) and [Japan legal guide](legal_en.md).

Keep operator-only JSON outside the deployment root. The Infinite Stream operator JSON contains both Bearer tokens; when using `--operator`, the bundled server rejects POSIX files readable by group or other users, so set `chmod 600`. Windows ACLs are not validated by the code; restrict access to the file and its parent directory, verify effective permissions with `icacls`, and heed the startup warning. If you use environment variables instead, keep the service environment and process access restricted.

On platforms supported by NGINX's [`disable_symlinks`](https://nginx.org/en/docs/http/ngx_http_core_module.html#disable_symlinks) (including Linux, FreeBSD and Solaris), the static example sets `disable_symlinks on` to prevent a link under the document root from serving an outside file. The directive relies on `openat()` and `fstatat()` support and may not protect other platforms. Keep deployment artifacts as regular files and restrict write access to the document root; with another server, configure and verify its symlink policy.

Both Nginx samples reject unmatched `Host` headers with a default server. Access the loopback listeners as `localhost` or `127.0.0.1`. If a TLS gateway proxies to these samples, set its upstream `Host` to one of those accepted names; do not make the catch-all accept arbitrary hosts.

Canary notifications show that an HTTP request reached the URL; they do not identify the attacker or who read the file. Email/document security scanners, link previews and internal monitoring may request URLs automatically. Correlate provider metadata, known scan times and hosting logs before treating a contact as an incident.

1. Prepare an isolated document root that production applications, backups and search indexes do not ingest. Choose names and access controls appropriate to your environment.
2. If needed, obtain URLs from your canary service, then select one method in the GUI and generate its deployment files. Use a publicly reachable monitor in case a crawler or AI agent follows the link. Non-public IPs, `localhost`, local-only hostnames such as `.local`, and single-label names are rejected, but DNS is not resolved; verify that the hostname does not resolve to an internal address from the deployment environment. Standalone generation accepts one URL. Encrypted Deep Nest, Directory Maze and Encoding Maze accept up to 400 URLs, one per line, and record URL-to-file assignments in the private operator inventory. Each generated canary placement consumes one URL; assignments use every supplied URL once before reusing any. URLs beyond the number of generated placements remain unused. Alerts from a reused URL cannot identify the exact file. Deep Nest applies its canary percentage, which may further reduce placements. Keep all URLs and the operator inventory private. URLs are never rewritten: accepted values, including signed query strings, are preserved verbatim; leading or trailing whitespace is rejected instead of being trimmed. Both .env layouts reject '$' because dotenv parsers differ in variable expansion; the standard layout also rejects single quotes, while the development/production note layout accepts them. Choose another file format when an .env layout rejects the URL.

When the `.env` development/production note layout includes an active environment URL, use `example.invalid` or confirm that you own the custom host and route it only to an isolated test endpoint without production authentication. Crawlers or agents following that URL may send requests to it. The generator does not resolve or contact the host; the ownership confirmation is not stored in settings and must be given again after import.
3. Deploy only files marked for deployment. Extract deployment ZIPs into the isolated document root; place standalone deployment files there directly as appropriate. Keep `.operator.json` and `.inventory.json` in a separate restricted location. Fill in `owner`, `deployment_location` and `deployed_at` in the inventory. The `inventory_file` field names the inventory JSON itself; the verifier checks that it matches the primary artifact's expected inventory filename and does not collide with a listed artifact. Its own digest is omitted because embedding that digest would be self-referential. `operator_files` and `operator_artifacts` list the other operator companions. It records SHA-256 digests for deployment and operator files, plus a review date 30 days after creation. Compare against a protected inventory copy after transfer; a hash alone cannot detect replacement of both an artifact and its inventory. It does not automatically expire or remove anything. Browser downloads are not automatically excluded from Git: the ignore file excludes common generated formats placed in the repository root, while source fixtures under directories such as `examples/` remain trackable. Operator and inventory JSON remain ignored everywhere. Prefer an ignored directory such as `generated/` or store files outside the repository, and check `git status --short` before committing.

For post-transfer checks, the integration-samples ZIP includes `examples/verify_inventory.py`. Use an inventory.json obtained from a trusted store as the reference, and point the verifier to the deployed-artifact and operator-artifact directories. The command reports that the inventory itself is trusted and not verified; protect it and compare it through a separate trusted channel. The inventory itself must be a regular, stable file while it is read. The verifier rejects symbolic links and directory junctions anywhere in the deployment tree, and rejects files reached through links that resolve outside their designated directory. The deployment, operator and package directory roots must also be regular directories; symlinks, junctions and other reparse points at the root are rejected. Every artifact record must contain a valid byte count; a size mismatch is reported before hashing starts. Each file has a 128 MiB verification limit. The verifier resolves the artifact path immediately before opening, after opening and after hashing, and compares the opened file descriptor with the path entry. Detected path changes and final-component link swaps fail verification. This is not an atomic filesystem snapshot, so restrict writes to the directories during and after verification. If the recorded filename is absent, a browser-style `name (1).ext` file is accepted only when its size and SHA-256 match the inventory. Protect the directory against writes after verification; a successful check describes only the files at check time. It checks extracted deployment files, not the ZIP used to transfer them. Add `--package-directory` only if you also want to verify retained source ZIPs. Use distinct `--directory` and `--operator-directory` locations. The verifier fails if the inventory or listed operator-only artifacts (including browser-renamed copies such as `file (1).json`) appear anywhere in the deployment tree, if the operator directory is nested under that tree, or if deployment and operator directories are the same.

The deployment-tree scan and the renamed-file scan each have a separate limit of 100,000 entries. If either scan exceeds its limit, narrow the relevant directory and retry.

```powershell
python examples/verify_inventory.py .\private\inventory.json --directory .\deployed --operator-directory .\private
# Also verify original ZIP packages retained separately
python examples/verify_inventory.py .\private\inventory.json --directory .\deployed --operator-directory .\private --package-directory .\downloads
```

It exits with code 1 for missing or changed files and code 2 for invalid input or inventory. Without `--package-directory`, deployment ZIP hashes are not checked. The verifier does not authenticate the inventory itself; do not retrieve it from a location where an attacker could replace both the artifacts and the inventory.
4. Configure download logging. `examples/nginx-decoy.conf` is a loopback static-hosting example with Basic authentication and an http-level 10-second request-header timeout that also applies to the default server for unmatched Host headers. The decoy server limits request bodies to 16 KiB, applies a 10-second gap timeout while receiving them, and keeps idle connections for at most 15 seconds; these limits help bound rejected upload attempts and idle connections, not total request duration. It paces requests at 5 per second per observed source, delays up to 10 excess requests, and returns 429 beyond that burst. It also caps active requests at 10 per observed source and 50 total, returning 429 above either limit; the total cap also bounds distributed sources. Nginx starts counting a request only after the complete request headers are read, so retain the 10-second header timeout. See the [official limit_conn module documentation](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html). Tune these values for your deployment. Behind a gateway, the source may appear as the gateway; configure real-IP handling only for explicitly trusted proxy addresses. This adds friction to repeated retrievals but distributed sources can bypass per-source limits. It allows only GET/HEAD, denies operator/inventory files (including common browser duplicate names), the default `adg-settings.json` and its duplicate names at any depth below the document root, and VCS metadata paths, but still requires a dedicated document root containing deployment files only. Custom-named settings or operator files cannot be identified by these rules and must stay outside the document root. Its loopback listener requires the TLS gateway to run on the same host. For a remote gateway, change both `listen` addresses to the same private interface and firewall access to that gateway; never expose the sample directly to the public network. In the gateway's proxy location, set `proxy_set_header Host 127.0.0.1:9081;` (or another accepted name) so the named server handles the request. Integrate its http/server sections, password file and log permissions into your infrastructure. Do not replace your production configuration wholesale.
5. Send structured contact events to your existing monitoring system. `examples/access_events.py` removes query strings and fragments, then emits a stable SHA-256 identifier in a separate route_id field by default. Identical routes remain linkable; this is pseudonymization, not anonymization or encryption, and predictable routes can be guessed. To match an event to the URL route that serves the decoy file (not the canary service URL), run `python examples/access_events.py --hash-route` and enter the exact route as Nginx logged it in `$uri`; input is hidden and the output uses the same `/sha256/<digest>` format as the route_id field. This hashes the path only, not the host or query string. Use `--show-path` only for temporary troubleshooting when a readable route is necessary; it may expose a canary token. The original nginx access log still contains the raw path, so restrict access and configure retention and rotation there too. Events retain the HTTP method and status code, plus body_bytes_sent and request_seconds when the Nginx log contains valid values. The bundled Nginx examples also log `limit_req_status` and `limit_conn_status`; the latter variable requires Nginx 1.17.6 or newer. the converter validates them as `rate_limit_status` (PASSED, DELAYED, REJECTED or dry-run variants) and `connection_limit_status` (PASSED, REJECTED or dry-run rejection). The cloud-review parser preserves both fields. DELAYED confirms that Nginx applied request pacing, while a connection-limit rejection identifies the concurrency cap. request_seconds is the total server-side request time, including any delay and response transfer, not an isolated measurement of throttling. Nginx writes access logs at request completion. When request_seconds is present, the converter estimates the request start by subtracting it from that timestamp and uses the estimate for event time; it preserves the original as request_completed_at. This is a millisecond-resolution server-side estimate, not a client-side timestamp. A 2xx response or server-side byte/time count does not prove that the client received the entire body. The script does not send email or webhooks. Alert on `event=decoy_contact`, assign an owner and configure deduplication in your logging platform.
Both supplied Nginx examples record a per-request 32-character hexadecimal `request_id`. The converter preserves its validated lowercase form and Cloud Review carries it into the finding. This lets your log platform join a decoy-contact finding to the Infinite Stream's `stream_started`/`stream_ended` events. The ID is a correlation value, not proof of identity.

6. Test download detection and canary URL use separately, through to the notification recipient. Record notification_tested_at. Check expected scanner activity before deployment.

```sh
python examples/access_events.py < /var/log/nginx/adg-access.jsonl
# Only for troubleshooting; readable paths may contain secret tokens.
python examples/access_events.py --show-path < /var/log/nginx/adg-access.jsonl
tail -F /var/log/nginx/adg-access.jsonl | python -u examples/access_events.py
```

For saved logs in PowerShell, use `--input` so the script reads the UTF-8 bytes directly instead of receiving shell-converted text:

```powershell
python examples/access_events.py --input .\adg-access.jsonl
```

Reprocessing logs repeats events. The sample omits IPs, query strings, bodies, cookies, Authorization and User-Agent. Correlate with existing authentication audit IDs if you need account/session attribution. The source nginx log retains raw paths and remains sensitive if they contain tokens. A contact is a review signal, not proof of intrusion: previews and legitimate scanners can trigger it. Correlate with existing authentication, WAF and EDR evidence before revoking sessions, rotating genuine credentials or isolating hosts. Do not automatically ban an IP based on one event.

For Infinite Stream, use `examples/nginx-stream-proxy.conf` from the integration-samples ZIP as a starting point. Merge its `limit_req_zone`, `limit_conn_zone` and `log_format` directives into the `http {}` context, and place its server blocks inside that context. The sample sets a 10-second request-header timeout at http level, including the default server for unmatched Host headers. The backend socket also closes a connection after five seconds without activity; a write blocked for five seconds ends that stream with `write_timeout`. Nginx proxy timeouts do not extend this backend limit. The bandwidth limit is not a cumulative quota. The theoretical continuous payload is rate (KiB/s) x 84.375 = MiB/day (about 675 MiB/day at 8 KiB/s, or 5.27 GiB/day at 64 KiB/s); HTTP/TCP overhead is additional. Estimate costs and prepare bandwidth monitoring and a stop procedure. It is a loopback example for the default port 9080 and path `/exports/archive.sql`. Basic authentication gates clients; nginx then replaces Authorization with the backend access Bearer token. The stream route allows only GET and HEAD; other methods are rejected before proxying request bodies. GET and HEAD bodies are also not forwarded: the sample disables upstream request-body forwarding and clears the Content-Length header, while limiting incoming bodies to 16 KiB and body-read inactivity to 10 seconds. Idle client connections are limited to 15 seconds. These are request/resource bounds, not a cap on the stream response duration. The sample applies a per-source-IP request limit (10 requests/minute with a burst of 5) before proxying, to slow repeated authentication attempts. Tune it for expected reconnects and shared NAT addresses; it is friction, not protection against distributed sources. If a separate gateway is in front, `$binary_remote_addr` may identify that gateway instead of the client. Only configure nginx real-IP handling for explicitly trusted proxy addresses; do not trust arbitrary forwarded headers. Keep the main Nginx configuration free of the backend token: copy the included `examples/nginx-stream-token.conf.example` to `/etc/nginx/adg-stream-token.conf`, replace the placeholder there with `ADG_STREAM_TOKEN` from the operator-only JSON, and restrict that file to the Nginx configuration administrator (for example, root-owned mode 0600). Include it inside the exact stream `location`, alongside its other `proxy_set_header` directives; Nginx does not merge `proxy_set_header` directives from the enclosing server level when the location defines its own. Never put the admin token there. Keep `/stop` and `/health` private. POST /stop disables stream delivery but does not terminate the process or close the management listener; stop the process with Ctrl+C or its service manager. The Nginx sample also caps concurrent requests at 8 per observed source and 8 globally, returning 429 above either limit. The generated backend setting permits 1 to 8 streams, so its `max_streams` remains the effective delivery cap and may be lower. Nginx counts connections only after request headers are fully received; the source address may represent a shared gateway. The configured nginx read/send timeouts limit inactivity gaps, not total response age; a separate absolute duration cap in a CDN or gateway can still truncate the stream and must be checked. Nginx normally writes access logs after a response completes, so this endless response may not be logged until disconnect. For prompt detection, use request-start logs from your authentication gateway. For network access, place the listener behind your existing TLS-terminating authenticated gateway. Update the sample if you change the stream port, path or auth file. This is an example to adapt, not a production configuration to replace yours with.

The backend listens on `127.0.0.1:9080`; the authenticated nginx example listens on `127.0.0.1:9082` and forwards to the backend. A TLS gateway on the same host can target port 9082. If the gateway is on another host, bind nginx only to a private interface and firewall access to that gateway; never expose this sample directly to the public network. Create the `auth_basic_user_file` with your existing `htpasswd` tooling, store it outside the web root, and restrict read access to the nginx service account. Basic credentials must travel only through a TLS-protected gateway; do not expose this loopback sample directly over public HTTP. In the config, include `log_format` and `limit_req_zone` under nginx's `http {}` context; the `server {}` block also belongs inside `http {}`.

The Python service emits secret-free JSON `stream_started` and `stream_ended` events to stdout immediately. An authenticated `HEAD` request to the stream route returns metadata without opening a stream and emits `stream_probe`; it does not consume a stream slot. Events omit the configured path, credentials and client IPs. Capture stdout with the service manager and forward it to a protected log collector or alert rule; `stream_started` gives a signal before an endless response completes. End events include `payload_bytes_sent`, server-side elapsed `duration_ms`, and a coarse `reason`: `operator_stop`, `client_disconnected`, `write_timeout`, `transport_error`, or `handler_error`. `payload_bytes_sent` counts payload blocks only after the complete block write and flush succeed; it excludes HTTP/TCP framing and headers. Bytes from a partially written block that fails are omitted. This is not a transport acknowledgement or proof of client receipt. `duration_ms` measures server-side stream lifetime and likewise does not confirm receipt. An unexpected exception outside stream handling emits `request_handler_error` with only its exception class name; the default traceback and client address are suppressed. These fields aid triage but are not root-cause diagnoses. Each event and `GET /health` carry a process-specific `run_id`; counters reset on process restart, so group records by `run_id` when aggregating across restarts; pair `stream_started` and `stream_ended` with both `run_id` and `stream_id`, since stream IDs restart with each process. The supplied Nginx JSON access log records time, method, path, status, bytes and duration, but omits client IP and authentication identity. For prompt detection, use request-start events from your gateway. If client attribution is needed, configure the trusted gateway to record the minimum required identifier, protect access to those logs and apply your retention policy; do not trust arbitrary forwarded headers. The sample does not deliver alerts by itself.

For event correlation, the server adds a 32-character hexadecimal `request_id` to stream events and successful stream or authenticated HEAD response headers. The supplied Nginx sample generates that ID, forwards it to the server and includes it in its completion-time access log. Join those records by `request_id` in your log platform; pair stream start/end events using `run_id` and `stream_id` too. This does not make the Nginx log immediate: use the server's `stream_started` event or a trusted gateway's request-start log for prompt detection.

Invalid Bearer credentials now emit `stream_auth_failure_summary` for the first failure and, per scope/method pair, at most once every 10 seconds. A timer flushes any suppressed increase at the end of that interval even if no later failure arrives. The event includes the process `run_id` and cumulative failure count, but no credential, route, client address or client-supplied request ID. Basic-auth failures rejected by Nginx never reach the Python service; review the protected Nginx or gateway logs for those attempts and for client attribution. The summary event is a detection signal, not a block or a complete audit trail.

Cloud Review also accepts this event format in JSONL/JSON/CSV and displays the timestamp, auth scope, HTTP method, cumulative failure count and a well-formed run_id. Select an application log containing these summaries to review invalid Bearer attempts, including those made by scripts or AI agents, alongside other audit logs. The source log is processed locally and is not sent to an external service.

See [`examples/cloud-review-stream-auth-sample.csv`](../examples/cloud-review-stream-auth-sample.csv) for a minimal CSV example. Select it in the UI to review one fictional summary. For real service logs, retain the event, timestamp, scope, method and failures_total columns.

On clean process shutdown (Ctrl+C or service-manager stop), the server signals active streams to stop and waits for request handlers to finish before closing. This gives them time to emit their end events. A blocked socket write may take up to five seconds to time out. `POST /stop` does not terminate the process; stop it separately afterward.

## Honeyword routing and fake state

Apply the existing pre-authentication rate limits first. A genuine password match continues through the complete existing MFA and authorization flow. Only an incorrect genuine password, a designated privileged username and a registered honeyword hash match may create a decoy-only session. All other inputs fail normally. Never let a client flag or an AI select the authentication outcome.

Reject overlap between genuine and fake passwords at enrollment and password changes. Use your established password hashing, generic failure messages and rate limits; avoid account enumeration through timing differences. Never issue a production token for a honeyword match. Production APIs must reject decoy tokens, and decoy routes must reject production sessions; do not let either session type authorize the other environment. Use a distinct decoy cookie with Secure, HttpOnly, SameSite, appropriate host/path isolation, expiry and CSRF protection. Do not collect genuine MFA codes in the fake environment.

The framework-neutral sample defaults to 100 sessions, 15-minute expiry and a 3-second pending state. Constructor limits are 1,000 sessions, 60 minutes and 30 seconds, respectively; setting `delay=0` applies updates immediately and returns `status: applied`. It also provides validated updates, read-after-update consistency and revocation. When full, `create()` raises `DecoyCapacityError`; an attacker can deliberately fill this bounded capacity. Catch this in the authentication adapter, record a password-free capacity event, and return the same generic authentication failure used for other invalid credentials. Never fall through to genuine authentication or issue a production token. Monitor capacity-rejection events and set a limit appropriate for expected concurrent use. It stores a SHA-256 digest of each random session ID as the in-memory lookup key, not the raw bearer ID; this reduces direct token exposure in a state dump but does not protect session data or a token stolen from the client. While pending, `read()` returns the remaining wait in `retry_after_seconds`; a later read shows the applied value. It is thread-safe within one process, but state is process-local: multiple workers or hosts will not see each other's sessions, and a restart loses all state. Production use needs a shared store and coordination. It is not an authentication server and provides no browser UI, persistent storage, MFA or notifications.

`DecoyState` does not write audit events. Add logging in the authentication adapter after a honeyword match and session creation, and send it to your existing protected audit sink. Do not log entered genuine or fake passwords, session IDs/cookies or canary URLs. Record only the minimum needed for investigation, such as event type, time and route. `examples/access_events.py` converts Nginx HTTP delivery logs; it does not record authentication-adapter events.

```python
from examples.decoy_state import DecoyCapacityError, DecoyState
store = DecoyState()
session_id = store.create()  # Only after a trusted server classifies a honeyword match.
store.update(session_id, {"retention_days": 60})
store.read(session_id)       # pending, then applied with retention_days=60 after 3 seconds
store.revoke(session_id)
```

Framework-neutral adapter pseudocode for capacity exhaustion:

```python
try:
    session_id = store.create()
except DecoyCapacityError:
    audit("honeyword_capacity_rejected")  # Never include the submitted password.
    return generic_authentication_failure()  # Do not retry genuine authentication.
```

For adaptive behavior, add a deterministic `export_requested -> queued -> ready` state machine. Keep counts, processing order and downloads consistent. If an LLM writes response text, restrict its output and actions; never grant it arbitrary commands, SQL, outbound URLs or production access.

## Evaluating AI-directed prompts

Use a harness with no network access, real credentials, production data or write-capable tools. Use only synthetic documents and harmless task detours, then record whether the agent deviates from its original task or repeats a review. Do not ask the agent to open URLs, disclose data, invoke tools or change state. Merely consulting a document is not evidence of successful prompt injection. An agent may ignore the instruction, and AI-generated scripts may never pass documents to an AI at runtime.

Treat attacker-controlled log paths as untrusted data in your own analysis tools. Enforce tool permissions in code, not just prompts. See [OWASP's prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [HTTP canary trigger behavior](https://docs.canarytokens.org/guide/http-token.html).

## Evaluation and retirement

Compare decoy/no-decoy scenarios with harmless mock secrets, no prior knowledge and identical budgets. Separate crawlers, AI-generated scripts, document-reading agents, partial/parallel downloads and offline analysis. Add a deception-aware condition that knows common decoy fingerprints and can probe the isolated decoy; watch for resource exhaustion and loss of audit-log integrity. A 2026 preprint reports that, in its specific evaluation, adding counter-deception raised correct honeypot identification from 19% to 97%, and also describes active disruption of specific OT honeypots. These results do not establish that the same attacks or rates apply to this tool or general deployments ([Rouxii](https://arxiv.org/abs/2609.26555)). Keep the decoy isolated from production and preserve its logs in a protected sink. Record first contact, notification arrival, response completion, mock-secret access, candidate classification accuracy, false positives and defender CPU/memory/egress. Time spent on decoys alone is not success: check whether response finishes before secret retrieval or whether budget limits cause more secrets to be missed.

## Keyed access-log route identifiers

The default `/sha256/<digest>` route identifier is stable but unkeyed; a reader can guess low-entropy paths offline. For logs that may contain canary tokens in the path, create a random key in a restricted operator-only directory and pass it to every converter instance:

```sh
mkdir private
chmod 700 private
python -c "from pathlib import Path; import secrets; p=Path('private/adg-route.key'); f=p.open('xb'); f.write(secrets.token_bytes(32)); f.close()"
chmod 600 private/adg-route.key
python examples/access_events.py --hash-key-file private/adg-route.key < /var/log/nginx/adg-access.jsonl
python examples/access_events.py --hash-key-file private/adg-route.key --hash-route
```

On Windows PowerShell, create a dedicated directory, restrict its ACL before creating the key, then run the converter with the same key:

```powershell
if (Test-Path .\private) { throw 'Choose a new, empty private directory before continuing.' }
New-Item -ItemType Directory -Path .\private | Out-Null
icacls .\private /inheritance:r /grant:r "$($env:USERDOMAIN)\$($env:USERNAME):(OI)(CI)F"
python -c "from pathlib import Path; import secrets; p=Path('private/adg-route.key'); f=p.open('xb'); f.write(secrets.token_bytes(32)); f.close()"
python examples/access_events.py --input .\adg-access.jsonl --hash-key-file .\private\adg-route.key
python examples/access_events.py --hash-key-file .\private\adg-route.key --hash-route
```

The key must contain at least 32 random bytes. On POSIX, the converter rejects a key file accessible by group or other users; use `chmod 600`. On Windows, use a new empty directory; the example ACL grants access only to the current account. If a service account must read the key, grant that identity explicitly and inspect `icacls` output for broad or inherited entries. Keep the key outside deployment and source-control directories. The converter emits `/hmac-sha256/<digest>` identifiers, so use the same key for route lookup and event processing. Losing or rotating the key creates a new identifier space. The original Nginx log still contains raw paths and needs its own access controls and retention policy. Without `--hash-key-file`, the converter retains the backward-compatible, guessable SHA-256 identifier.

Do not combine `--show-path` with `--hash-key-file`; the converter rejects this contradictory request so a mistaken flag cannot silently expose readable paths instead of keyed identifiers.
