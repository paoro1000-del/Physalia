# Deployment, detection and response for small teams

## Synthetic names

Sample names are formed by independently combining 1,000 public surname candidates with 1,000 given-name candidates. Surnames are ordered by estimated population; given names come from curated popular male and female candidates and spelling variants, not an official nationwide ranking. A combination may match a real person. Associated records remain synthetic. See `THIRD_PARTY_NOTICES.md` for attribution and license. A name alone may still be personal information; do not treat generated names as information about the real people they may match.

## Findings and changes

The GUI presents one method at a time, including its mechanism, threat scenario, conditions and limitations.

The Static Decoy Portal switches its palette, information panel, navigation and page content for operations, shared documents, business archives or records management. When a canary URL is supplied, it is placed in a file-list entry, a purpose-specific sidebar link and an action in the information panel. Clicking a link may send a request to the monitor; opening the page alone does not. These placements appear in both the HTML preview and deployment ZIP. Do not publish files containing the canary URL, and keep the operator-only mapping separate.

Fake Trap monitoring is off by default. A monitoring URL (canary URL) is the page address that records contacts. For external monitoring, enter an HTTPS URL issued by a monitoring service. For a local check, use the local URL supplied by Physalia; it works only while the app is running on the same PC. Only when the option is enabled and a URL is entered does the generated page send a GET request through an embedded image as it loads. The service may receive ordinary HTTP request metadata such as source IP and User-Agent. No custom API implementation is needed.

Path Maze offers Windows, Unix-like and macOS profiles. Each profile changes directory naming and the relative path budget: Windows uses short names that avoid reserved names and forbidden characters, Unix-like uses lowercase FHS-inspired names, and macOS uses names such as `Library` and `Application Support`. Defaults create twenty levels, 890 branches per level and three files per folder, with about 124,481 folders and 497,925 ZIP entries. Actual extraction also depends on the destination path, filesystem and OS settings, so verify in a dedicated test location. HTML links stay inside the ZIP; it contains no filesystem symlinks, executable scripts or external requests. Keep the operator-only map separate from the deployment ZIP and account for added files in backups and searches. Automated, parallel or offline enumeration can still map the tree quickly; delay is not guaranteed.

Fake Trap generates eight business-portal pages, including sign-in review, request receipt, maintenance, new-device review, access requests, sync status and security-setting updates. When monitoring is off or the URL field is blank, the page sends no external request. When enabled with a monitoring-service canary URL, an embedded image sends a GET request as the page loads. Mail scanners and link previews may also create contacts, so a contact alone does not identify an attacker. The page does not authenticate or collect additional information. The design hypothesis is that an AI agent inspecting the HTML structure or rendered page may spend time reassessing its context. It cannot reliably fool AI; low-level tools that classify static HTML directly and automation that never renders the page are less affected. Deploy only to an authorized decoy path and prevent accidental access by legitimate users. Configure access logs and internal notifications on the hosting side; an alert is not guaranteed to arrive before exfiltration. Do not publish generated files containing the URL, and keep the accompanying private inventory separate from the deployed page. Data Dilution and Privilege Honeyword Session are technology overviews only.

Ransomware Decoy Flood creates a deployment ZIP with four to eight synthetic files and a separate Python script that replenishes changed or deleted decoys in the same directory. Run the operator-only script manually with Python 3.11 or later against the extracted directory. It checks about once per second and logs changes to `tripwire-alerts.jsonl`. Replacements and bytes are unlimited by default; optional `--max-files` and `--max-bytes` limits apply to each run. It does not replenish while stopped, and replacements from previous runs are not tracked after restart. A full disk can disrupt operations and recovery and may not stop overwriting existing files. If an attacker repeatedly processes replenished files, the additional work may cause a delay.

Path Maze creates a finite tree of ordinary folders and synthetic files without filesystem symlinks. HTML index pages contain relative links into the archive tree. Its operator-only JSON lists the deployment paths. It is intended to increase review and selection work during manual searches or when important-file search tools include decoys among their candidates, potentially burying genuine files. Classification, ranking or automatic filtering may remove decoys; bulk enumeration and parallel or offline analysis can reduce the effect. Delay and missed targets are not guaranteed. Searches, backups and sync also process the added files, so check operational impact.

Sparse Decoy creates a synthetic file with a large logical size and small initial allocation. On a supporting filesystem, reads from sparse ranges return zeros, and writing nonzero data may allocate disk space ([Windows sparse-file behavior](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-file-operations)). A process that reads and writes the entire file without optimizing sparse regions may incur additional work; sparse-aware handling, large-file exclusions or partial processing may reduce or remove the effect. Encrypted output, copies, sync or backups may consume the logical size and disrupt operations or recovery. This does not stop ransomware or guarantee delay. Test at a small size, monitor free capacity, and keep the operator-only file list separate. The extension is cosmetic; the content does not match that format.

For cross-OS deployment, choose the sparse TAR output in the generator. It is an uncompressed TAR with GNU PAX sparse format 1.0 metadata: a logical length and an extent map accompany the actual data ranges, so the archive remains small while preserving the intended large logical file. Extract on the target with GNU tar or bsdtar, such as `tar -xf <archive.tar>`. Verify logical size with `ls -lh` and allocated blocks with `du -h`. A generic extractor may not restore holes and can allocate the full logical length. The extension remains cosmetic. The archive contains the deployable synthetic file; keep the accompanying operator inventory private and separate.

This is a simple early-warning tripwire, not ransomware protection software. Reads and exfiltration alone do not trigger it. An attacker can stop the monitor or change and restore files between checks, and real data may be damaged first. Place tripwires where normal applications do not write; protect the script and log separately from the watched and public directories. Use existing OS protections and endpoint detection to restrict writes or contain a device. On Windows, [Microsoft Defender Controlled Folder Access](https://learn.microsoft.com/en-us/defender-endpoint/controlled-folder-access-overview) can restrict changes to protected folders by untrusted applications. Without a recoverable copy or change history, destroyed data cannot be restored.

The GUI also explains ordinary use and potentially prohibited conduct under Japan's Unauthorized Computer Access Act. See [the Japanese-law guide](legal_en.md) for assumptions, sources and other applicable legal considerations.

The same guide and the GUI also present a general U.S. federal and state law perspective. These Japanese and U.S. assessments are general interpretations, not guarantees. Consult a legal professional familiar with the applicable jurisdictions and configuration before deployment.

Every generated artifact has a separate private inventory with its hash, settings and lifecycle fields.

Start with static decoys, your existing web logs and notification system. No LLM subscription or new always-on service is needed for this configuration. Deception supplements access control; it does not prevent arbitrary exploitation or guarantee an AI attacker will follow document instructions.

## Baseline defenses remain necessary

Deception detects or delays some post-entry activity; it does not prevent initial access, replace authorization checks, or contain an incident by itself. Keep internet-facing systems and VPN appliances inventoried and patched, use MFA for privileged accounts, limit repeated login attempts, retain and review authentication and access logs, restrict lateral access between systems, and maintain recoverable backups. Add decoys alongside these controls and connect their alerts to an owner who can respond. Do not wait for a decoy alert before containing a confirmed compromise. The Personal Information Protection Commission's October 2026 warning describes incidents involving unpatched vulnerabilities, weak authentication, delayed detection, excessive cross-system access and API weaknesses, and calls for layered security measures. [PPC warning, revised October 7, 2026](https://www.ppc.go.jp/files/pdf/261007_warning.pdf) (Japanese).

This is a practical starting order for small teams, not a claim that every organization has the same legal duties or risk profile. Prioritize systems that process personal data and internet-facing identity infrastructure, assign an owner for patching and alert review, then deploy a small number of monitored decoys in an isolated path.

### Inventory public files and discovery endpoints

AI-assisted reconnaissance can download public JavaScript bundles, source maps, runtime configuration and API descriptions, then probe the routes they reveal. This possibility is a reason to reduce unnecessary exposure and retain access logs; it does not mean every crawler follows the same sequence.

For each public hostname, including staging and forgotten subdomains:

1. Inventory reachable applications, directories, API routes and cloud identity integrations using only systems and accounts you control.
2. Confirm that real `.env` files, `.git` metadata, database files, backups, editor files and deployment archives cannot be downloaded. Inspect response bodies as well as status codes because single-page-app fallbacks may return normal HTML with `200` for nonexistent paths.
3. Restrict source maps, debug routes and API descriptions such as Swagger/OpenAPI when they are not intended to be public.
4. Have an authorized operator review existing access and identity logs for unusual bursts across paths, repeated authentication or recovery attempts, and unexpected successful responses after failures. Correlate with approved changes and known scanners; an IP or User-Agent alone does not establish identity or intent.
5. Keep unknown-path behavior ordinary and consistent. Do not route every missing path to a decoy page; it can expose a fingerprint and hide real routing mistakes. Place a small number of decoys on plausible, monitored paths after reviewing actual exposure.

The generator does not scan production hosts or verify public-file exposure. This repository includes no reconnaissance-log parser or automatic classification. See [Recording and Manually Reviewing Canary Contacts](log-review-guide_en.md) for a manual log-review approach.

## Additional controls for organizations using AI agents

Decoys do not restrict the identities, tool permissions or host permissions available to an AI agent. OWASP's 2026 Q3 roundup describes an MCP distribution campaign that attempted to change tool definitions after approval and steer agents toward local credentials; no compromise was confirmed. A separate Q2 roundup describes researcher-controlled validation in which crafted error telemetry influenced coding-agent execution. These reports do not mean every agent is vulnerable, but approval-time review alone may not be enough. [OWASP 2026 Q3 roundup](https://genai.owasp.org/2026/10/08/genai-and-agentic-ai-exploit-roundup-q3-2026/) [OWASP 2026 Q2 roundup](https://genai.owasp.org/2026/07/08/genai-and-agentic-ai-exploit-roundup-q2-2026/) [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/?lang=us)

Do not assume an AI-assisted attacker will stop when a person would become tired. Microsoft reported multiple cases reaching privileged cloud access in under three hours, while Wiz reported some ARTEX-related sessions lasting 24–30 hours and adapting when blocked. These are observations from specific investigations, not a universal attacker profile. Plan for both fast access to persistence and sustained follow-on work: a decoy delay matters only if monitoring and response interrupt useful data access or persistence first. [Microsoft investigation](https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/) [Wiz research](https://www.wiz.io/blog/artex-in-the-wild-storm-0940-expands-targeting-of-it-and-software-vendors)

For a small organization, apply these controls through existing identity, endpoint and audit systems:

1. **Give each agent a distinct identity and least privilege.** Avoid shared high-privilege accounts and long-lived administrator tokens. Use short-lived credentials scoped to the required resources and actions. Do not give a read-only task write, send or delete permissions.
2. **Govern MCP servers and tool-definition changes.** Record approved publishers, versions, tool names and argument schemas. Review diffs and require re-approval on updates. `examples/agent-tool-approval-template.json` in the integration-samples ZIP is a record template. If recording a schema digest, hash the exact approved schema file with SHA-256 and compare against that same file. The template does not retrieve or monitor tool definitions or enforce an allowlist. Remove unused MCP integrations and deny agent access to credential stores, SSH keys and cloud configuration by default.
3. **Isolate execution.** Restrict repositories, shells, filesystems and network access per task. Treat model-generated paths, commands, URLs and search filters as untrusted; validate them against allowlists in host-side code. Do not expose secrets through environment variables or working directories unnecessarily, and limit outbound destinations.
4. **Require independent approval for high-impact actions.** Do not let model judgment alone send email, publish externally, release code, grant permissions, change credentials, delete data or make payments. Enforce human review or a separate policy check in the tool implementation.
5. **Trace and stop execution.** Correlate agent identity, caller, tool and version, target resource, result, child processes and outbound connections in existing logs. Prepare stop and token-revocation procedures. A decoy contact is an investigation signal; it does not prove an agent's execution history or a compromise.

Review Entra and other identity/cloud audit records in the identity provider or logging service your organization already uses. This app does not ingest or automatically classify logs. For decoy-contact fields, see [Recording and Manually Reviewing Canary Contacts](log-review-guide_en.md).

## Smallest useful deployment

### Canary provider logs and privacy

For a same-PC check, Physalia automatically sets a local canary page URL at startup. It records contacts to Physalia's loopback listener at `127.0.0.1`; other hosts cannot reach it. Samples created in one session share the URL, and earlier URLs stop working after restart. For production use, publish a canary page over HTTPS at a location reachable from external networks, then use that page's URL in the decoy. The local log keeps up to 500 events in memory and is cleared when Physalia exits.

The Canary page shows the source IP, User-Agent, language, client hints and other metadata supplied with same-PC requests. When JavaScript runs in a browser, it can also report screen dimensions, time zone, approximate CPU and memory, GPU information and automation flags to the local server. The source IP is normally `127.0.0.1`; browser and OS labels are estimates from the User-Agent. Clients may omit or falsify values, which cannot identify a sandbox or attacker. Authorization headers, cookies, arbitrary canary request bodies, referrer URLs and query strings are not retained; browser reports accept only fixed fields. Local processes can access the interface, so restrict access at the OS level and determine the purpose and handling under your organization's rules and applicable law.

To host your own canary destination in an isolated environment, download the homepage kit at the bottom of the Canary page. It contains an HTML/CSS/JavaScript page, a Python standard-library logging server, and Japanese and English setup guides. For external hosting, use an HTTPS reverse proxy with access controls. The kit writes request and browser information to JSONL, explains location collection before requesting browser permission, and leaves log access, retention and deletion to the operator.

When a canary URL is requested, its provider and hosting operator may receive request metadata such as the source IP address, time and User-Agent. Check the provider's actual collection, retention and storage-region terms. Requests may come through a VPN, relay or crawler, so treat an IP address as an investigation clue rather than proof of the attacker's identity. Review the provider's privacy notice, log access and deletion controls, subprocessors and storage regions. Do not put customer IDs or other identifying data in the URL; align log purpose, retention and access with your internal policy. The Personal Information Protection Commission explains that device identifiers may be personal-related information even when they do not identify an individual by themselves. The legal treatment depends on how the information is combined and used; see the [General Guidelines](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/) and [Japan legal guide](legal_en.md).

Keep operator-only JSON outside the deployment root. The Infinite Stream operator JSON contains both Bearer tokens; when using `--operator`, the bundled server rejects POSIX files readable by group or other users, so set `chmod 600`. Windows ACLs are not validated by the code; restrict access to the file and its parent directory, verify effective permissions with `icacls`, and heed the startup warning. If you use environment variables instead, keep the service environment and process access restricted.

On platforms supported by NGINX's [`disable_symlinks`](https://nginx.org/en/docs/http/ngx_http_core_module.html#disable_symlinks) (including Linux, FreeBSD and Solaris), the static example sets `disable_symlinks on` to prevent a link under the document root from serving an outside file. The directive relies on `openat()` and `fstatat()` support and may not protect other platforms. Keep deployment artifacts as regular files and restrict write access to the document root; with another server, configure and verify its symlink policy.

Both Nginx samples reject unmatched `Host` headers with a default server. Access the loopback listeners as `localhost` or `127.0.0.1`. If a TLS gateway proxies to these samples, set its upstream `Host` to one of those accepted names; do not make the catch-all accept arbitrary hosts.

Canary notifications show that an HTTP request reached the URL; they do not identify the attacker or who read the file. Email/document security scanners, link previews and internal monitoring may request URLs automatically. Correlate provider metadata, known scan times and hosting logs before treating a contact as an incident.

Standalone generation accepts one URL. Directory Maze and Encoding Maze accept up to 400 URLs, one per line, and record URL-to-file assignments in the private operator inventory. Browser downloads are not automatically excluded from Git: the ignore file excludes common generated formats placed in the repository root, while source fixtures under directories such as `examples/` remain trackable. Operator and inventory JSON remain ignored everywhere. Prefer an ignored directory such as `generated/` or store files outside the repository, and check `git status --short` before committing.

For post-transfer checks, the integration-samples ZIP includes `examples/verify_inventory.py`. Use an inventory.json obtained from a trusted store as the reference, and point the verifier to the deployed-artifact and operator-artifact directories. The command reports that the inventory itself is trusted and not verified; protect it and compare it through a separate trusted channel. The inventory itself must be a regular, stable file while it is read. The verifier rejects symbolic links and directory junctions anywhere in the deployment tree, and rejects files reached through links that resolve outside their designated directory. The deployment, operator and package directory roots must also be regular directories; symlinks, junctions and other reparse points at the root are rejected. Every artifact record must contain a valid byte count; a size mismatch is reported before hashing starts. Each file has a 128 MiB verification limit. The verifier resolves the artifact path immediately before opening, after opening and after hashing, and compares the opened file descriptor with the path entry. Detected path changes and final-component link swaps fail verification. This is not an atomic filesystem snapshot, so restrict writes to the directories during and after verification. If the recorded filename is absent, a browser-style `name (1).ext` file is accepted only when its size and SHA-256 match the inventory. Protect the directory against writes after verification; a successful check describes only the files at check time. It checks extracted deployment files, not the ZIP used to transfer them. Add `--package-directory` only if you also want to verify retained source ZIPs. Use distinct `--directory` and `--operator-directory` locations. The verifier fails if the inventory or listed operator-only artifacts (including browser-renamed copies such as `file (1).json`) appear anywhere in the deployment tree, if the operator directory is nested under that tree, or if deployment and operator directories are the same.

The deployment-tree scan and the renamed-file scan each have a separate limit of 100,000 entries. If either scan exceeds its limit, narrow the relevant directory and retry.

```powershell
python examples/verify_inventory.py .\private\inventory.json --directory .\deployed --operator-directory .\private
# Also verify original ZIP packages retained separately
python examples/verify_inventory.py .\private\inventory.json --directory .\deployed --operator-directory .\private --package-directory .\downloads
```

It exits with code 1 for missing or changed files and code 2 for invalid input or inventory. Without `--package-directory`, deployment ZIP hashes are not checked. The decoy server limits request bodies to 16 KiB, applies a 10-second gap timeout while receiving them, and keeps idle connections for at most 15 seconds; these limits help bound rejected upload attempts and idle connections, not total request duration. It paces requests at 5 per second per observed source, delays up to 10 excess requests, and returns 429 beyond that burst. It also caps active requests at 10 per observed source and 50 total, returning 429 above either limit; the total cap also bounds distributed sources. Nginx starts counting a request only after the complete request headers are read, so retain the 10-second header timeout. See the [official limit_conn module documentation](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html). Tune these values for your deployment. Behind a gateway, the source may appear as the gateway; configure real-IP handling only for explicitly trusted proxy addresses. This adds friction to repeated retrievals but distributed sources can bypass per-source limits. It allows only GET/HEAD, denies operator/inventory files (including common browser duplicate names), the default `adg-settings.json` and its duplicate names at any depth below the document root, and VCS metadata paths, but still requires a dedicated document root containing deployment files only. Custom-named settings or operator files cannot be identified by these rules and must stay outside the document root. Its loopback listener requires the TLS gateway to run on the same host. For a remote gateway, change both `listen` addresses to the same private interface and firewall access to that gateway; never expose the sample directly to the public network. In the gateway's proxy location, set `proxy_set_header Host 127.0.0.1:9081;` (or another accepted name) so the named server handles the request. Integrate its http/server sections, password file and log permissions into your infrastructure. Do not replace your production configuration wholesale.

For Infinite Stream, use `examples/nginx-stream-proxy.conf` from the integration-samples ZIP as a starting point. Merge its `limit_req_zone`, `limit_conn_zone` and `log_format` directives into the `http {}` context, and place its server blocks inside that context. The sample sets a 10-second request-header timeout at http level, including the default server for unmatched Host headers. The backend socket also closes a connection after five seconds without activity; a write blocked for five seconds ends that stream with `write_timeout`. Nginx proxy timeouts do not extend this backend limit. The bandwidth limit is not a cumulative quota. The theoretical continuous payload is rate (KiB/s) x 84.375 = MiB/day (about 675 MiB/day at 8 KiB/s, or 5.27 GiB/day at 64 KiB/s); HTTP/TCP overhead is additional. Estimate costs and prepare bandwidth monitoring and a stop procedure. It is a loopback example for the default port 9080 and path `/exports/archive.sql`. Basic authentication gates clients; nginx then replaces Authorization with the backend access Bearer token. The stream route allows only GET and HEAD; other methods are rejected before proxying request bodies. GET and HEAD bodies are also not forwarded: the sample disables upstream request-body forwarding and clears the Content-Length header, while limiting incoming bodies to 16 KiB and body-read inactivity to 10 seconds. Idle client connections are limited to 15 seconds. These are request/resource bounds, not a cap on the stream response duration. The sample applies a per-source-IP request limit (10 requests/minute with a burst of 5) before proxying, to slow repeated authentication attempts. Tune it for expected reconnects and shared NAT addresses; it is friction, not protection against distributed sources. If a separate gateway is in front, `$binary_remote_addr` may identify that gateway instead of the client. Only configure nginx real-IP handling for explicitly trusted proxy addresses; do not trust arbitrary forwarded headers. Never put the admin token there. Keep `/stop` and `/health` private. The Nginx sample also caps concurrent requests at 8 per observed source and 8 globally, returning 429 above either limit. The generated backend setting permits 1 to 8 streams, so its `max_streams` remains the effective delivery cap and may be lower. The backend listens on `127.0.0.1:9080`; the authenticated nginx example listens on `127.0.0.1:9082` and forwards to the backend. A TLS gateway on the same host can target port 9082. If the gateway is on another host, bind nginx only to a private interface and firewall access to that gateway; never expose this sample directly to the public network. Create the `auth_basic_user_file` with your existing `htpasswd` tooling, store it outside the web root, and restrict read access to the nginx service account. Basic credentials must travel only through a TLS-protected gateway; do not expose this loopback sample directly over public HTTP. In the config, include `log_format` and `limit_req_zone` under nginx's `http {}` context; the `server {}` block also belongs inside `http {}`.

The Python service emits secret-free JSON `stream_started` and `stream_ended` events to stdout immediately. An authenticated `HEAD` request to the stream route returns metadata without opening a stream and emits `stream_probe`; it does not consume a stream slot. Events omit the configured path, credentials and client IPs. Capture stdout with the service manager and forward it to a protected log collector or alert rule; `stream_started` gives a signal before an endless response completes. End events include `payload_bytes_sent`, server-side elapsed `duration_ms`, and a coarse `reason`: `operator_stop`, `client_disconnected`, `write_timeout`, `transport_error`, or `handler_error`. `payload_bytes_sent` counts payload blocks only after the complete block write and flush succeed; it excludes HTTP/TCP framing and headers. Bytes from a partially written block that fails are omitted. This is not a transport acknowledgement or proof of client receipt. `duration_ms` measures server-side stream lifetime and likewise does not confirm receipt. An unexpected exception outside stream handling emits `request_handler_error` with only its exception class name; the default traceback and client address are suppressed. These fields aid triage but are not root-cause diagnoses. Each event and `GET /health` carry a process-specific `run_id`; counters reset on process restart, so group records by `run_id` when aggregating across restarts; pair `stream_started` and `stream_ended` with both `run_id` and `stream_id`, since stream IDs restart with each process. The supplied Nginx JSON access log records time, method, path, status, bytes and duration, but omits client IP and authentication identity. For prompt detection, use request-start events from your gateway. If client attribution is needed, configure the trusted gateway to record the minimum required identifier, protect access to those logs and apply your retention policy; do not trust arbitrary forwarded headers. The sample does not deliver alerts by itself.

For event correlation, the server adds a 32-character hexadecimal `request_id` to stream events and successful stream or authenticated HEAD response headers. The supplied Nginx sample generates that ID, forwards it to the server and includes it in its completion-time access log. Join those records by `request_id` in your log platform; pair stream start/end events using `run_id` and `stream_id` too. This does not make the Nginx log immediate: use the server's `stream_started` event or a trusted gateway's request-start log for prompt detection.

Invalid Bearer credentials now emit `stream_auth_failure_summary` for the first failure and, per scope/method pair, at most once every 10 seconds. A timer flushes any suppressed increase at the end of that interval even if no later failure arrives. The event includes the process `run_id` and cumulative failure count, but no credential, route, client address or client-supplied request ID. Basic-auth failures rejected by Nginx never reach the Python service; review the protected Nginx or gateway logs for those attempts and for client attribution. The summary event is a detection signal, not a block or a complete audit trail.



On clean process shutdown (Ctrl+C or service-manager stop), the server signals active streams to stop and waits for request handlers to finish before closing. This gives them time to emit their end events. A blocked socket write may take up to five seconds to time out. `POST /stop` does not terminate the process; stop it separately afterward.

## Honeyword routing and fake state

Apply the existing pre-authentication rate limits first. A genuine password match continues through the complete existing MFA and authorization flow. Only an incorrect genuine password, a designated privileged username and a registered honeyword hash match may create a decoy-only session. All other inputs fail normally. Never let a client flag or an AI select the authentication outcome.

Reject overlap between genuine and fake passwords at enrollment and password changes. Use your established password hashing, generic failure messages and rate limits; avoid account enumeration through timing differences. Never issue a production token for a honeyword match. Production APIs must reject decoy tokens, and decoy routes must reject production sessions; do not let either session type authorize the other environment. Use a distinct decoy cookie with Secure, HttpOnly, SameSite, appropriate host/path isolation, expiry and CSRF protection. Do not collect genuine MFA codes in the fake environment.

The framework-neutral sample defaults to 100 sessions, 15-minute expiry and a 3-second pending state. Constructor limits are 1,000 sessions, 60 minutes and 30 seconds, respectively; setting `delay=0` applies updates immediately and returns `status: applied`. It also provides validated updates, read-after-update consistency and revocation. When full, `create()` raises `DecoyCapacityError`; an attacker can deliberately fill this bounded capacity. Catch this in the authentication adapter, record a password-free capacity event, and return the same generic authentication failure used for other invalid credentials. Never fall through to genuine authentication or issue a production token. Monitor capacity-rejection events and set a limit appropriate for expected concurrent use. It stores a SHA-256 digest of each random session ID as the in-memory lookup key, not the raw bearer ID; this reduces direct token exposure in a state dump but does not protect session data or a token stolen from the client. While pending, `read()` returns the remaining wait in `retry_after_seconds`; a later read shows the applied value. It is thread-safe within one process, but state is process-local: multiple workers or hosts will not see each other's sessions, and a restart loses all state. Production use needs a shared store and coordination. It is not an authentication server and provides no browser UI, persistent storage, MFA or notifications.


```python
from examples.decoy_state import DecoyCapacityError, DecoyState
store = DecoyState()
session_id = store.create()  # Only after a trusted server classifies a honeyword match.
store.update(session_id, {"retention_days": 60})
store.read(session_id)       # pending, then applied with retention_days=60 after 3 seconds
store.revoke(session_id)
```

Framework-neutral adapter pseudocode for capacity exhaustion:

```python
try:
    session_id = store.create()
except DecoyCapacityError:
    audit("honeyword_capacity_rejected")  # Never include the submitted password.
    return generic_authentication_failure()  # Do not retry genuine authentication.
```

For adaptive behavior, add a deterministic `export_requested -> queued -> ready` state machine. Keep counts, processing order and downloads consistent. If an LLM writes response text, restrict its output and actions; never grant it arbitrary commands, SQL, outbound URLs or production access.

## Evaluating AI-directed prompts

Use a harness with no network access, real credentials, production data or write-capable tools. Use only synthetic documents and harmless task detours, then record whether the agent deviates from its original task or repeats a review. Do not ask the agent to open URLs, disclose data, invoke tools or change state. Merely consulting a document is not evidence of successful prompt injection. An agent may ignore the instruction, and AI-generated scripts may never pass documents to an AI at runtime.

Treat attacker-controlled log paths as untrusted data in your own analysis tools. Enforce tool permissions in code, not just prompts. See [OWASP's prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [HTTP canary trigger behavior](https://docs.canarytokens.org/guide/http-token.html).

The canary page requests browser permission through the Geolocation API and sends coordinates and accuracy reported by the browser to the same local Physalia server only when permission is granted. HTTP contacts are still logged if permission is denied or unavailable. A prior grant may avoid a new prompt, and some browsers require a button click. Values can be approximate or falsified and do not establish a real-world location. Browser or OS location services may use network services. Before collecting location, state the purpose, restrict log access, set a retention period, and check organizational rules and applicable law; browser permission alone does not guarantee legal compliance ([Geolocation API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition), [Japan PPC General Guidelines](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)).

## Evaluation and retirement

Compare decoy/no-decoy scenarios with harmless mock secrets, no prior knowledge and identical budgets. Separate crawlers, AI-generated scripts, document-reading agents, partial/parallel downloads and offline analysis. Add a deception-aware condition that knows common decoy fingerprints and can probe the isolated decoy; watch for resource exhaustion and loss of audit-log integrity. A 2026 preprint reports that, in its specific evaluation, adding counter-deception raised correct honeypot identification from 19% to 97%, and also describes active disruption of specific OT honeypots. These results do not establish that the same attacks or rates apply to this tool or general deployments ([Rouxii](https://arxiv.org/abs/2609.26555)). Keep the decoy isolated from production and preserve its logs in a protected sink. Record first contact, notification arrival, response completion, mock-secret access, candidate classification accuracy, false positives and defender CPU/memory/egress. Time spent on decoys alone is not success: check whether response finishes before secret retrieval or whether budget limits cause more secrets to be missed.

Use [`examples/deception-study-metadata-template.json`](../examples/deception-study-metadata-template.json) from the integration samples to record study design conditions separately from run-event data. Its required fields are blank until you fill them. The bundled [`scripts/check_study_metadata_schema.py`](../scripts/check_study_metadata_schema.py) validates completed files against [`examples/deception-study-metadata-template.schema.json`](../examples/deception-study-metadata-template.schema.json), a JSON Schema Draft 2020-12 document. Run `python scripts/check_study_metadata_schema.py path/to/study-metadata.json`. The validator is bounded to 2 MiB and uses only the Python standard library. Keep credentials, canary URLs, production details and personal data out of the template.

Public templates and example.invalid addresses can be distinguishing clues. Adapt document structure to your environment without importing real personal data or directing clients to third-party systems. On retirement, remove deployed paths/files, revoke canary tokens and decoy sessions, stop streaming processes and fill in retired_at. Keep patching, MFA, least privilege and restorable backups independently maintained.
