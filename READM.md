# AiDeceptionGuard

English | [日本語](README_ja.md)

A local defensive deception toolkit for individual developers and small organizations. Generate synthetic decoy artifacts, review identity and cloud activity logs locally, and use the included deployment examples to add monitoring and response steps in systems you control. Generated files are not deployed automatically; operators remain responsible for isolation, access controls, monitoring and response.

## Quick start

- On GitHub, select **Code → Download ZIP** and extract it, or clone the repository. The launch scripts are in the extracted or cloned folder.
- Python 3.11–3.14 is required; the launchers look for 3.14 first, then 3.13, 3.12 and 3.11. Start the app with [`start_windows.bat`](start_windows.bat) on Windows or [`sh start_unix.sh`](start_unix.sh) on macOS/Linux. The first run creates a virtual environment and installs the reviewed, pinned dependencies. See the [first-sample guide](docs/quickstart_en.md) for Python setup.
- New here? In **First sample**, the defaults create one standalone HTML file for Service management with 25 fictional records. Create it, then preview it from the results area. Choose **Create sample web page (HTML + deployment ZIP)** when you want a site to deploy. Select an operations, shared-documents, business-archive or records-management context. The deployment ZIP downloads automatically and contains `index.html` plus six fictional PDF, Excel and CSV files. Without a monitoring URL, all six open from the page. With one, a listed filename links to the monitor instead of opening its matching document; the other five open locally. The page has no login. The `.env` sample is decoy-only; do not load it into a real application or production configuration. For a database, choose a preset; its fields and synthetic row count are shown before you create it.
- The app saves files locally and does not deploy them. Add a canary URL by expanding **Add a monitoring service URL** and entering an HTTPS URL issued by your monitoring service. The generator copies it unchanged into supported samples and never contacts it. Without a URL there is no alert; creating, downloading or ordinarily opening a file does not request it. After deployment, a crawler, link preview or user may request it and create a monitoring event.

The tool aims to deceive and delay attackers during exploration after intrusion and during assessment or use of stolen information. ## Product overview and data handling

For canary contacts, the app provides a [guide to recording and manually reviewing logs](docs/log-review-guide_en.md), including a fictional JSON Lines sample, privacy guidance and review steps. It has no feature for ingesting and automatically classifying an operator's existing logs, and it ships no log-ingestion or detection tools.

The Decoy Database now includes 14 editable profiles: customers, card inventory, companies, password vault, orders, sales transactions, invoices, employees, user management, API credential inventory, vendors, support tickets, assets and cloud resources. It accepts up to 10,000 synthetic rows and 30 columns; generated SQLite files are capped at 32 MiB to bound local memory use. Payment card PAN/CVV values and real credential hashes are never generated. Password vault rows contain random synthetic strings with no linked real account or authentication service. API credential rows include service, fictional owner, scope, environment and rotation metadata; their synthetic key previews cannot authenticate. Credential status, rotation date and last-used time are generated consistently. Telephone values use the NANPA-reserved fictional, non-working 555-0100-0199 range ([NANPA](https://www.nanpa.com/numbering/555-line-numbers)). With the Japanese UI selected, human-readable candidate values such as products, industries, roles and cloud service/environment names are generated in Japanese; table and column identifiers and some status values remain English for interoperability. Cloud endpoint slugs stay ASCII under the reserved `.invalid` domain.

Financial amount columns use a lower-value-skewed synthetic distribution instead of a uniform spread. When a row uses JPY, these amounts are whole numbers; other currencies use two decimal places. Order totals follow the chosen item and quantity. The Orders, Sales, Card Inventory, Password Vault and Support Tickets templates can reuse fictional people across rows, with matching names and email addresses. Vendor risk tiers influence annual-cost ranges and review recency. Asset inventory status is reflected in the age of its last check. Asset names are paired with matching categories when the configured candidates include them. When the filename is blank, the generated database name follows the selected profile.

Cloud inventory endpoints are derived from the selected service and environment and always use the reserved `.invalid` domain. The generated endpoint is inert and is not resolved or contacted.

The GUI presents one method at a time with a scenario, a flow diagram, expected conditions, limits and detection/response prerequisites. Detailed explanations and legal perspectives can be expanded. Encrypted Deep Nest intentionally creates multiple formats within that selected method. See the [deployment and response guide](docs/deployment_en.md) for implemented features, static hosting and Infinite Stream nginx examples, structured access events and a framework-neutral fake-session state component. Authentication integration, notification delivery and deployment remain operator tasks.

Assume some attackers know common decoy fingerprints and actively probe decoy services. In one 2026 preprint evaluation, adding counter-deception raised correct honeypot identification from 19% to 97%; the same work reports disruption of specific OT honeypots. These results do not establish this tool's effectiveness or general attack rates ([Rouxii](https://arxiv.org/abs/2609.26555)). Keep decoys isolated from production, cap resources and protect logs. See the [evaluation](docs/deception_evaluation.md) for scope and limitations.

Each method includes a general assessment under Japan's Unauthorized Computer Access Act and a U.S. federal and state law perspective. See [the legal guide](docs/legal_en.md) for assumptions, sources and other issues. These are general interpretations; consult a legal professional familiar with the relevant jurisdictions and configuration before deployment.

Use **Save settings** / **Load settings** to reuse generator settings and database columns. Canary URL fields, URL-typed inputs and ownership confirmations are excluded. Values entered in owned decoy-domain fields remain in the JSON, but their confirmation checks are cleared; confirm ownership again after loading. Custom names and free-text candidates are retained: **URLs or secrets entered in free text are not automatically removed**. Never enter real records or secrets, and keep settings JSON operator-only.

Save/load rejects some recognizable credential and payment-card patterns but does not check free-text URLs. During generation, free text is checked for unapproved URLs, email addresses, public domains, IP addresses and common credential/card patterns; dedicated canary URL and attested owned-domain fields are validated separately. These are limited format checks, not comprehensive secret or endpoint detection. Use `example.invalid` for fictional endpoints. Settings saved with earlier versions may not load if the form or schema has changed.

Each generated artifact has a separate operator-only `*.inventory.json` with settings, canary placement and unused URL counts, SHA-256 digests for deployment and operator artifacts, owner/deployment fields and a review date. If a canary context was selected automatically, the chosen profile, field and display label are recorded there. Compare against a protected inventory copy after transfer; a hash cannot detect replacement of both the artifact and its inventory. Keep it with operator files, outside deployed content. This is an operator-managed inventory, not automatic token expiry. The inventory JSON names itself in `inventory_file`; it omits its own digest to avoid a self-reference. `operator_files` and `operator_artifacts` cover the other operator companions.

## Features

- **Manual log guidance**: Learn which limited metadata to record after a decoy contact and how an authorized operator can review it in an existing logging system. No operator-log ingestion or automatic classification is included.
- **Canary file**: Choose `.env`, text, JSON, CSV, HTML, PDF, Excel (`.xlsx`), PowerPoint (`.pptx`), or SQLite (`.db`). Configure names, titles, record counts, and an HTTPS canary URL.
- **Encrypted Deep Nest**: Generate branching, layered AES-encrypted ZIPs with synthetic files, optional format variation and optional canary URLs. Each ZIP gets a generated password. The design aims to add post-exfiltration decryption and selection work, and may make attackers doubt separately collected genuine encrypted files; the effect is unverified. The generated decoy contains no real secrets.
- **Decoy Database**: Configure a table and columns, data generators, numeric ranges, candidate values, and up to 10,000 synthetic records.
- **Static Decoy Portal**: Generate a standalone HTML preview and a deployment ZIP containing the linked `index.html` and six synthetic PDF, Excel or CSV documents. An optional canary URL replaces one file-list link. Configure hosting access logs separately; the portal has no login or built-in telemetry.
- **Fake Trap**: Generate a static unusual-access warning, reported message or authentication spinner. These are display-only: detection, reporting, authentication and external communication are not performed. Configure access logging and alerts separately at the host.
- **Technology overviews**: Data Dilution proposes mixing real and synthetic records to complicate selection and use after a leak. Privilege Honeyword Session proposes routing a registered decoy-password match to an isolated decoy session. Both are explanations only; production database changes and authentication integration are not implemented.
- **Infinite Stream**: Generate an authenticated endless-response server with configuration and startup instructions.
- **Directory Maze**: Generate a finite static directory tree with optional cross-links and synthetic files. Dynamically changing URLs and HTTP redirects are an unimplemented extension idea.
- **Encoding Maze**: Generate scenario-matched synthetic files in one selected format and package them with layered Base64, Hex or other encodings.

Method cards carry overlapping tags for intended roles: Detection, Delay, Decoy lure, Post-leak disruption and AI attacks considered. These describe design aims, not guaranteed results or AI-exclusive effectiveness; some methods require separate monitoring and alert configuration.

Decoy Database also aims to make post-exfiltration verification inconclusive even after time and expense have been spent. A seller who mistakes a decoy for genuine data and resells it might lose credibility if a buyer identifies it as fake and shares that assessment. Neither effect has been measured, and genuine databases may still leak separately.

Generated files are saved through your browser's download function; the application does not automatically upload or deploy them. Store deployment files and their operator-only companions outside the repository or in its ignored `generated/` directory. `.gitignore` excludes common generated formats in the repository root only; generated databases or documents in subdirectories can still be added. `.operator.json`, `.inventory.json` and ordinary `.env` files are ignored in any directory, but `.env.example` is an exception that can be tracked. Do not rely on ignore rules alone: check `git status --short` before committing and keep real data, secrets, passwords and canary URLs out of Git.

ZIP member timestamps are varied within the 180 days before generation. They do not represent the source files' real creation history and must not be used as audit evidence or a reliable timeline.

## Setup and launch

Python 3.11 is the minimum source requirement. The launch scripts and CI matrix support Python 3.11 through 3.14 on Windows, Ubuntu and macOS. Python 3.15 is not in the matrix and is not verified. `requirements.txt` and `requirements-dev.txt` pin direct and transitive dependencies with `==` and include SHA-256 hashes for the published distributions. Install with `--require-hashes --no-deps --only-binary=:all:` to allow only prebuilt wheels. `--no-deps` alone does not pin isolated build dependencies when pip builds a source distribution. If no compatible wheel is available, do not remove the binary-only flag without reviewing the publisher, build requirements and target platform. Pip verifies the selected wheel against the reviewed hash and does not resolve undeclared runtime dependencies. This detects distribution bytes that differ from the reviewed hashes, provided the requirement files came from a trusted commit or release. It does not detect malicious code in an approved distribution or an unreviewed change to the versions or hashes. Review lock-file changes and verify signed commits, tags or package provenance where available. CI runs `pip check` after installation, rejects floating or unhashed dependency specifications, and checks each pinned release against known vulnerability data published by PyPI. That advisory check does not detect issues absent from PyPI's data, including vulnerabilities in native libraries. Before updating a dependency, review the publisher and package contents, deliberately update the version and its hashes, and run the project checks. The following example uses Windows PowerShell:

For a guided setup, use Python 3.11–3.14. The launch scripts prefer Python 3.14 when available, then fall back to 3.13, 3.12 or 3.11.

On Windows, double-click [`start_windows.bat`](start_windows.bat) for a guided first launch. It looks for Python 3.14, 3.13, 3.12 or 3.11 through the Windows `py` launcher, then falls back to supported `python` or `python3` commands, creates `.venv`, installs the reviewed hash-pinned dependencies only on first setup or when `requirements.txt` changes, and opens the browser. First-time setup may need internet access to download pinned packages that are not already cached; the launcher does not upgrade packages to newer releases. Keep its console open and press `Ctrl+C` there to stop the server. If the default port is already in use, pass another port, for example `start_windows.bat --port 8766`. If you prefer manual setup, check that the selected command resolves to a supported Python version before creating the virtual environment.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install --require-hashes --no-deps --only-binary=:all: -r requirements.txt
.\.venv\Scripts\python app.py
```

On macOS or Linux, run [`sh start_unix.sh`](start_unix.sh) for a guided launch. It looks for versioned Python 3.14, 3.13, 3.12 or 3.11 commands and falls back to `python3` or `python` when those resolve to a supported version. It creates `.venv`, installs reviewed hash-pinned dependencies only on first setup or when `requirements.txt` changes, and opens the browser. Missing pinned packages may require internet access. It does not upgrade packages to newer releases. Press `Ctrl+C` in the terminal to stop the server. If the default port is already in use, pass another port, for example `sh start_unix.sh --port 8766` or `start_windows.bat --port 8766`. For manual setup, use the virtual environment's Python executable directly:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes --no-deps --only-binary=:all: -r requirements.txt
.venv/bin/python app.py
```

Open the displayed address, `http://127.0.0.1:8765/`, in your browser. Press `Ctrl+C` in the terminal to stop the server. To use a different port, run `python app.py --port 8766`; use `--port 0` to select an available port. On macOS and Linux the virtual environment's Python executable is normally `.venv/bin/python`.

Use the language selector in the top-right corner to switch between Japanese and English. The browser remembers your choice, which also applies to generated Web pages. For English command-line messages, pass `--lang en` when starting or decrypting, for example `python app.py --lang en`. The default is Japanese.

## How canary tokens work

When a canary URL is requested, its provider and hosting operator will ordinarily receive request metadata such as the source IP address, request time and User-Agent. The fields collected, retention period and storage location vary by service. An IP address does not necessarily identify the attacker; the request may come through a VPN, relay or crawler. Before use, review the provider's privacy notice, who can access its logs, retention and deletion terms, subprocessors and storage regions. Do not put customer IDs or other identifying data in the URL. Depending on linkage and use, request metadata may be personal information or personal-related information under Japan's privacy law. The Personal Information Protection Commission explains that device identifiers can be personal-related information even when they do not identify a person by themselves ([General Guidelines](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)).

Obtain the canary URL separately from a canary service or another monitoring system. This application does not issue tokens, receive canary events, or send notifications. If you leave the URL blank, `.env` formats contain an inert `example.invalid` example URL; other formats omit the URL. Neither is a monitoring endpoint, so **no alert will occur**.

After a file is exfiltrated, a later URL request that reaches the monitoring endpoint can still provide an investigation lead. A relay, VPN or sandbox may make the observed IP describe an intermediary rather than the attacker; after redistribution, recipients and scanners may also request the URL. Keep URL-to-placement mappings in the private operator inventory and correlate alerts with known scans and other logs. No notification occurs if communication is blocked or the URL is never requested.

Use a publicly reachable monitoring endpoint in case a crawler or AI agent follows the link. Email/document security scanners and link-preview services may also request it automatically. A canary alert shows that the URL was requested; it does not identify who caused the request or who read the file. Correlate provider metadata and hosting logs with known scanners and expected traffic before treating it as an incident. Private IP addresses, `localhost`, local-only hostnames such as `.local` and `.internal`, and single-label hostnames are rejected. The tool does not resolve DNS; verify in the deployment environment that the supplied domain does not resolve to an internal address.

Standalone generation accepts one canary URL. Encrypted Deep Nest, Directory Maze and Encoding Maze accept up to 400 URLs, one per line, and record URL-to-file assignments in the private operator inventory. The result screen shows the placement count, distinct URLs used and unused URL count. Each generated canary placement consumes one URL; assignments use every supplied URL once before reusing any. URLs beyond the number of generated canary placements remain unused. When a URL is reused, an alert cannot identify the exact file. Deep Nest also applies its canary percentage, which can reduce the number of placements. Keep every URL and operator inventory private.

Reading a file alone does not trigger a URL-based canary. PDF, Excel, PowerPoint, and HTML contain ordinary hyperlinks; configuration files, JSON, and CSV contain endpoint values; most databases contain a connection table. The Password Vault template places the canary in one `login_url` record and records its row in the private inventory when that column uses a URL-capable Domain or Text type; if it was removed, renamed or changed to another type, the URL goes in a connection table. Opening files does not automatically contact these URLs. An alert requires actual access to the URL. Trigger conditions and notification delays depend on your service. Test before deployment. Treat embedded URLs as tokens and do not commit generated files to a public repository.

For standalone canary files, choose a service, billing, support or report context, or select one automatically, and optionally set the URL field name and visible link label. The selected context also changes the fictional record columns and values: service management uses cloud inventory, billing uses invoices, support uses tickets, and reports use sales records. `.env` uses the uppercase field name; JSON and CSV use it as written. CSV headers show both the readable label and the supplied field name, and the URL appears only in the first record. Excel places a labeled hyperlink on a worksheet named for the selected context, and SQLite uses a context-specific table. PDF/PowerPoint/HTML use a labeled link, and text includes the label and URL. PowerPoint includes all requested rows, split across slides with up to 10 records each. CSV values that could be interpreted as spreadsheet formulas are prefixed with an apostrophe to reduce that risk, which changes the raw CSV text. Excel strings are stored as text; generated files do not contain formulas or macros. Accepted provider-issued URLs are preserved verbatim and are never contacted by the generator; unsupported characters in .env layouts are rejected rather than rewritten.

This changes the surrounding context, not the token itself: the domain, URL structure and hyperlink metadata can still reveal it. No alert occurs without a configured URL and an actual access. These settings apply to the standalone canary generator; each other generator uses its own file layout.

Content, reference numbers, and fictional names vary between generations. Changing formats alone does not prevent decoy identification. Choose names and documents that fit the deployment environment and inspect them before use.

Leave the file name blank to get a format-appropriate name. Business-context prefixes, workflow labels and date suffixes vary across generated names, for example `customer_archive.db`, `quarterly_report_2026Q4.pdf` or `customer_export_v2.csv`. This adds variety but does not guarantee uniqueness or make names indistinguishable. Explicit names are preserved. A blank `.env` format keeps the conventional `.env` name.

For `.env`, the GUI's development/production switch layout produces `.env.development` by default; its suffix is configurable. The standard layout produces `.env`. A supplied base name produces `name.env` in either layout.

The standard `.env` layout wraps the canary URL in single quotes. Because `.env` parsers differ in variable expansion ([python-dotenv](https://github.com/theskumar/python-dotenv#variable-expansion), [Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax)), URLs containing `$` are rejected by both `.env` layouts; use another format. A URL containing a single quote can use the development/production note layout. Provider URLs are never rewritten; leading or trailing whitespace is rejected instead of being trimmed.

Some browsers remove a leading dot from direct downloads. For a filename beginning with `.env`, the GUI automatically downloads a deployment ZIP containing the exact filename. Extract the ZIP before deployment; a direct file link is also provided. Save the operator inventory JSON separately.

The key, active URL, suffix and both comments are editable. The suffix sets `APP_ENV` and the default URL host (for example, `staging` uses `staging.example.invalid`); a manually entered active URL should match the selected environment. The default `development` URL is `http://dev.example.invalid:8080`. Review active URLs and comments in Detailed settings before generating. For a host outside `example.invalid`, confirm that you own it and route it only to an isolated test endpoint without production authentication. A crawler or AI agent may send requests to the active URL; the generator does not resolve or contact it. Do not enter internal or production endpoints. The ownership confirmation is not saved in settings and must be given again after loading them. Internal hostnames, private IPs, fragments, whitespace and shell expansion characters are rejected. URL values are quoted. The regular URL-context field and label controls do not apply to this layout. The canary URL is preserved verbatim.

A normal `.env` parser ignores the comment: an alert requires someone or an agent to actually request the URL. Download or reading alone will not trigger it; configure server-side download logging separately. The URL and token provider's domain are still inspectable. Keep the generated decoy out of production application configuration.

## Nest configuration and passwords

The GUI supports:

| Setting | Options |
| --- | --- |
| Depth and branching | 1–8 layers, 1–3 child archives per parent; at most 40 encrypted ZIPs |
| Directories | Maximum depth 1–5 inside each ZIP; folder-name defaults follow the selected scenario and remain editable |
| Decoys | 0–10 files per ZIP; when mixing is enabled, about 75% use the selected primary format and the rest use weighted alternatives |
| Canaries | Independent 0–100% probability per decoy; 0% or a blank URL inserts no monitoring URL |
| Passwords | Word-based or fully random; lowercase, uppercase, digits, symbols; a 4–64 character range; custom word candidates |
| Gradual difficulty | Shorter passwords at the beginning; optional recovery-note decoys for the first two layers, all layers, or none |
| Recovery notes | Optional notes claim that part of the key is stored in a separate register; they disclose no password characters |

No manual password entry is needed. Every archive receives a distinct password. Word-based passwords start with a word but insert random letters, digits and symbols at randomized positions instead of using a fixed year or suffix pattern. If a candidate repeats, the generator switches to a random value with the same length and character classes. Optional recovery notes are attacker-facing decoys: they imply that a key register exists elsewhere but disclose no password characters. The configured withheld-character count changes only the note's wording; it does not reveal a fragment or reduce the password search space. Passwords remain in the separate operator-only JSON. With progressive length enabled, the default range starts at 9 characters and increases in deeper layers. Archives can be attacked offline and in parallel after download, so neither a successful guess nor delay is guaranteed. Consider fully random mode too. Notes vary across several operational formats to reduce identical boilerplate. **Even a 9–13 character password may be impractical to crack.** Offline solve time depends on the archive format and attacker hardware, and is not guaranteed. Omit notes if they would look suspicious in your environment.

Save all three outputs after generation:

1. `name_deployment.zip`: The deployment artifact. This ordinary delivery ZIP contains the outer AES-encrypted ZIP and, if selected, a recovery-note decoy. It contains no password characters. The encrypted ZIP contains decoys and child encrypted ZIPs.
2. `name.operator.json`: Download separately using the **operator-only** link. It lists every archive password, the generation mode used for each password, layer, internal path, clue-note location, canary location and per-document formats.
3. `name_deployment.zip.inventory.json`: Download separately as the lifecycle inventory. It contains artifact hashes, generation settings, canary URL details and format totals. Treat it as operator-only too; keep it with restricted access outside the deployment ZIP and never publish it. Save both JSON files in a restricted location. The page requires downloading every operator-only file before confirmation and warns before closing or leaving while they are unconfirmed. It also asks before a method change, settings load or new generation removes the current download links.

Use an AES-compatible ZIP tool to inspect archives; non-AES extraction tools cannot open them. The operator JSON is excluded from the deployment ZIP. ZIP file and folder names remain visible in listings. When format mixing is enabled, about 75% of documents use the selected primary format, with weighted alternatives such as Excel, SQLite and .env in the remainder. This setting varies document formats inside the encrypted nest. Format counts are recorded in both `*.inventory.json` and `.operator.json` as `format_counts`; the per-document `format` is in `.operator.json`. Canary placement is sampled independently per file, so the realized percentage can differ from the configured probability in small batches. Choose 100% to put a URL in every eligible decoy.

Encrypted nest generation is finite and bounded to 32 MiB of uncompressed decoy content, 64 MiB cumulatively across encrypted archives, and a 64 MiB deployment ZIP. Configurations with excessive nested-size amplification are rejected. Endless responses are provided separately by Infinite Stream. Generator checks establish file correctness, not attacker delay or defensive effectiveness.

New generation no longer uses the custom ADG format. The existing `python decrypt.py input.adg output.json --lang en` command remains for legacy ADG files only, reads regular files up to 64 MiB and never overwrites an existing output file. On POSIX, it creates output readable only by the owner. On Windows, output inherits the destination directory ACL; restrict that directory and verify effective permissions with `icacls`. Decrypted files may contain sensitive data; do not put them in public repositories or shared folders. The command does not handle the new ZIPs.

## Database columns

During generation, free-text inputs are checked for unapproved URLs, email addresses, public domains, IP addresses and recognizable common credential, private-key, JWT and Luhn-valid payment-card patterns. Dedicated canary URL and attested owned-domain fields are validated separately; reserved examples such as `example.invalid` are allowed. Settings save/import rejects common credential patterns but does not check URLs. These are narrow format checks, not comprehensive endpoint, secret or personal-data detection. Do not enter real data or secrets; settings JSON retains custom field names and candidate values.

Choose a profile for customers, card inventory, companies, password vaults, orders, sales transactions, invoices, employees, user management, vendors, support tickets, assets or cloud resources. A profile fills in a table and columns; edit them afterward or switch to **Custom** and add up to 30 columns. Generators include full names, login names, invoice/order/sales references, email, company, department, numeric ranges, dates, status, UUID, synthetic phone, `.invalid` domain and documentation-only IP. For candidate-based values, use `active|pending|archived`; for numeric ranges, use `100,5000`. The User Management preset separates a display name from a unique synthetic login name and contains no usable credentials.

With the Japanese interface, generated names, companies and departments use fictional Japanese values. Email addresses use corresponding romanized names. Rows with a company use a company-matched subdomain under reserved `example.invalid`; rows without one use `example.invalid`. The English interface uses English sample values.

To make a decoy fit your environment, replace company, department, status and text candidates with fictional terms that match your business. Candidate values reject live domains, IP addresses, URLs and email addresses; use reserved examples such as `example.invalid`. To provide candidate names or email-like values, change the column kind to Text. Company-associated email/domain values use company-matched subdomains under reserved `.invalid`; rows without a company use `example.invalid`. The dedicated email-domain field can override this with an owned domain reserved for an isolated decoy. For a more credible decoy database, you may supply a domain you own and dedicate to an isolated decoy. The generator does not resolve the domain or send mail, and requires an ownership/dedicated-use confirmation. Do not use a production mail domain or real mailboxes; route any inbound mail only to an isolated monitoring sink.

The invoice template generates issue and due dates in relation to payment status: open/pending invoices have future due dates, while overdue invoices have a past due date after the issue date.

The order template relates order age to status: pending and processing orders are recent, while shipped and complete orders are generally older.

Support tickets use open, pending, in-progress, resolved and closed states. Their opened timestamps are generated so unresolved tickets tend to be newer than closed tickets.

Employee profiles use onboarding, active, on-leave and offboarded states, with start dates generated to fit each status.

XLSX output stores generated strings as text cells. CSV has no cell-type metadata, so values that resemble formulas are prefixed with an apostrophe to reduce formula interpretation risk; the apostrophe remains in the CSV data. Spreadsheet import behavior varies, so verify CSVs in the spreadsheet application you use.

Card inventory deliberately omits payment card numbers and CVV; it uses a visibly nonfunctional `TEST-NOT-A-PAN-...` reference. Phone fields use the fictional, non-working `+1-202-555-0100` through `+1-202-555-0199` range reserved for entertainment and advertising, including in Japanese-language samples ([NANPA](https://www.nanpa.com/numbering/555-line-numbers)). The `expired` status gets a past expiry month; `active` and `suspended` get a future month. Password vault rows use randomly generated synthetic strings in a normal `password` column. Their default `login_url` values use an HTTPS URL shape under the reserved, non-resolving `.invalid` domain; they do not reach real authentication services. No real credentials or hashes are imported. These profiles are representative decoys, not importable production vaults. Company/vendor profiles derive a stable ASCII host from the fictional company name under `.invalid`. Built-in Japanese company names use readable romanized slugs; other Unicode names use IDNA. Records for one organization share the same inert domain. Long names are shortened with a deterministic suffix to fit DNS label limits. Table and column names allow up to 48 ASCII letters, digits and underscores.

In the Password Vault scenario, the optional **Owned decoy domain** setting replaces the default login hosts with `https://service-name.your-domain/service-specific-login-path` values. The generator does not resolve or contact the domain, but an attacker or crawler that opens a generated URL will. Enter a domain you control, confirm the attestation, provision a matching TLS certificate, and route wildcard DNS only to an isolated decoy without production authentication. These are not canary tokens; monitor DNS or web server logs for contact. This shared setting applies to the standalone database and non-`.env` outputs from Encrypted Deep Nest, Directory Maze and Encoding Maze; `.env` output uses its environment variable instead. Leave it blank to retain the non-resolving `.invalid` values.

An optional canary URL adds a connection table, except in Password Vault scenarios where it replaces one randomly selected synthetic `login_url` value; the private inventory records its path, field and record number. It never replaces the `password` value. Reading the database alone does not alert; the URL must be requested. An `id` field is a primary key, with lookup indexes for common email, domain and status fields. ## Deploying the three additional samples

### Infinite Stream

The server adds a correlation `request_id` to stream events and successful stream or authenticated HEAD responses. The supplied nginx example generates one per request, forwards it upstream, and records it in the completion-time JSON access log. In your log platform, join server events to nginx records by `request_id`; pair start and end events with `run_id` and `stream_id` as well. Normal nginx access logs may be delayed until the response completes, so use `stream_started` for prompt detection.

Invalid backend Bearer credentials emit a `stream_auth_failure_summary` event on the first failure and, per scope/method pair, at most every 10 seconds. A timer flushes any suppressed increase at the end of that interval even if no later failure arrives. It includes the cumulative failure count, but no credential, route, client IP or client-supplied request ID. Basic-auth failures rejected by Nginx never reach the Python process; use protected gateway/Nginx logs for those attempts and attribution.

When starting with the operator JSON, restrict the file to its owner on POSIX (`chmod 600`); the server rejects broader permissions. Windows ACLs are not validated: restrict access to the file and its parent directory, then verify effective permissions with `icacls`. The file contains both access and admin tokens.

The bandwidth limit is shared across all connections and is not a cumulative quota. At a continuous rate, the theoretical payload maximum is `rate (KiB/s) × 84.375 = MiB/day`: the default 8 KiB/s is about 675 MiB/day, and 64 KiB/s is about 5.27 GiB/day. HTTP/TCP overhead adds to this amount. Estimate network/cloud costs before deployment and prepare bandwidth monitoring and a stop procedure.

The backend listens on `127.0.0.1:9080`; the optional authenticated nginx proxy example listens on `127.0.0.1:9082` and forwards to it. A TLS gateway on the same host can target port 9082. For a remote gateway, bind nginx only to a private interface and firewall access to that gateway; never expose this sample directly to the public network.

Configure SQL/CSV/text content, path, port, **aggregate** bandwidth (1–64 KiB/s) and simultaneous streams (1–8). Paths use slash-separated ASCII letters, digits, `_`, `-` and `.` (up to 160 characters); `..`, dot-only segments and segments ending in a dot are rejected to avoid path normalization differences. Connected responses have no total duration or byte cutoff. Disconnects, operator stop or failures end the response. Data is generated incrementally rather than preallocated as a file. Row IDs increase and references are generated synthetic values. Financial amounts use a lower-value-skewed distribution; order totals are linked to the selected item and quantity. JPY amounts are whole numbers and other currencies use two decimal places.

The Infinite Stream nginx example limits repeated requests by source IP (10/minute with a burst of 5). Tune it for reconnects and shared NAT users. If nginx is behind another proxy, configure client IP handling only for trusted proxy addresses; arbitrary forwarded headers can let attackers evade the limit or affect other users.

For a GUI file name of `stream_sample`, extract into a dedicated directory and start with the private JSON kept outside it:

```powershell
Expand-Archive -LiteralPath .\stream_sample_deployment.zip -DestinationPath .\stream_sample
python .\stream_sample\serve.py --operator .\stream_sample.operator.json
```

Add `--lang en` to display CLI messages in English; Japanese is the default.

Only the Python standard library is required. The deployment ZIP includes the Apache-2.0 `LICENSE` with its bundled server source. The server listens on `127.0.0.1:9080` by default. Supply `ADG_STREAM_TOKEN` from operator JSON in the download request's `Authorization: Bearer ...` header. Terminate the process with `Ctrl+C`. To stop delivery while leaving the process and management endpoints running, use `POST /stop` with the separate `ADG_STREAM_ADMIN_TOKEN`. Streams stay disabled until restart. `GET /health` with the admin token reports the current `run_id`, active streams, starts, and `payload_bytes_sent` since process start; counters reset on restart, so group records by `run_id` when aggregating across restarts; end events use the same field for an individual stream and include a coarse `reason` label for operator stop, client disconnect, timeout, or transport/handler error. Authenticated HEAD probes return headers without streaming and emit a secret-free stream_probe event. This byte count excludes HTTP/TCP headers and framing. Each stream_ended event also reports duration_ms, the server-side elapsed time in milliseconds; it does not confirm client receipt. The stdout events carry a process-specific `run_id`; pair it with `stream_id` because stream IDs restart with each process. Tokens are excluded from the deployment ZIP and can alternatively be supplied through environment variables. Generated values are Bearer-compatible. If you set them manually, use different 32–256 character values containing only Bearer-safe ASCII characters (letters, digits, . _ ~ + / - and up to two trailing =); whitespace and quotes are rejected.
payload_bytes_sent counts payload blocks only after the complete block write and flush succeed. Bytes from a partially written block that fails are omitted; this is not a transport acknowledgement or proof that the client received the bytes.

The server rejects duplicate JSON object keys in its configuration and operator files, including keys that differ only by case. This prevents startup with ambiguous settings.

**Disconnect test clients after a few seconds, for example with `curl --max-time 3`.** This is a client testing limit, not a server response limit. Headers have a 10-second absolute deadline and a five-second inactivity timeout; stalled writes also time out after five seconds. None of these limits total streaming time.

For Infinite Stream in an existing Web deployment, proxy an isolated authenticated decoy route to the loopback server. A direct proxy targets the backend at `127.0.0.1:9080`; when using the supplied nginx Basic-auth example, a same-host TLS gateway targets `127.0.0.1:9082`, and nginx forwards to port 9080. For a remote gateway, bind nginx only to a private interface and firewall access to that gateway. Verify TLS, disable buffering/compression on each proxy hop, and check proxy timeouts. Nginx read/send timeouts limit inactivity gaps, not total response age; a separate absolute duration cap in a CDN or gateway can still truncate the stream. Keep `/stop` and `/health` outside external routes and never share the admin token with download clients. The supplied Nginx JSON access log also records `rate_limit_status`; `DELAYED` means the request was paced, while `request_seconds` measures the complete response. It omits client IP and authentication identity; use protected request-start gateway logs for attribution when required, and trust forwarded client-IP headers only from explicitly configured proxy addresses. GUI-driven launch/publication, production login integration, notifications, and event history are not implemented. See the generated README for details.

### Encoding Maze

Choose a business scenario, 1–20 candidates, 1–8 encoding layers, decoded format, and Base64, Base64url, Hex, percent encoding or Gzip+Base64. Generated content and the final deployment ZIP are each capped at 16 MiB. Each candidate gets independent synthetic records, with file names, titles and schemas that match the selected scenario and format. In the Password Vault scenario, non-`.env` candidates place a canary URL in a synthetic `login_url` record while leaving password values unchanged; `.env` files use the scenario's environment variable.

Each layer is JSON with `encoding` and `payload`. Decode the payload according to its encoding, then peel the next JSON layer until the original file is recovered. When Gzip is used, its header timestamp varies within the 180 days before generation and does not represent the source file's history. Operator JSON lists decode order, decoded format and SHA-256 for verification. This is not encryption and batch decoding is possible. Evaluate candidate comparison and content verification work. ## Current limitations

- The GUI and generators run locally and listen only on `127.0.0.1`. They do not protect against compromise of the local computer or other processes running as the same user.
- The Web page is static HTML. Production authentication integration, persistent configuration changes, access logs, canary event reception and notifications are not implemented. Infinite Stream is supplied as a separate verification server.
- Automatic deployment, cloud integrations, an installer and automatic token revocation are not implemented. Private inventory JSON is generated; users record deployment locations and manage removal.
- Documents use templates and synthetic data. Indistinguishability from production data and read-only canary alerts are not guaranteed.

### Evaluating deception and delay

Run authorized exercises using a mock target, comparing control and decoy conditions with equivalent starting information and time budgets. Include AI, scripts, parallel and offline analysis. Record target reach rates, time when reached, decoy contact, alerts, response and false positives from authorized users. Use [`examples/deception-study-metadata-template.json`](examples/deception-study-metadata-template.json) to document study conditions separately from run-event data. Its required fields are intentionally blank; fill them before validating a completed metadata file. The schema [`examples/deception-study-metadata-template.schema.json`](examples/deception-study-metadata-template.schema.json) rejects empty required descriptions, oversized fields and duplicate tool/telemetry entries; the bundled CLI also rejects whitespace-only required fields. The integration samples include a bounded, standard-library validator. Keep credentials, canary URLs, production details and personal data out of the metadata. Validate a completed copy with:

```bash
python scripts/check_study_metadata_schema.py path/to/study-metadata.json
```

The validator accepts the blank starter template without treating it as a completed study record. Try the illustrative event sample with:

```bash
python examples/evaluate_deception.py examples/deception-evaluation-sample.json
```

The sample includes an authorized control run and one authorized decoy contact that triggers an alert. Its rate and interval are illustrative, not a measured false-positive rate.

Attacker-group summaries also separate runs where the decoy was contacted before the mock secret, runs where the secret was reached first or without decoy contact, and runs that ended at the budget without reaching the secret. Events recorded at the same time are reported in `simultaneous_decoy_contact_and_secret` because their order is unknown; they are not counted as decoy-first or as delay. The decoy-to-secret median is based only on successful reaches after decoy contact; the no-reach duration is right-censored and is not counted as realized delay. Control-arm records must leave `decoy_time` null.

Attacker groups also report a Kaplan–Meier median time to the mock secret and restricted mean time without reaching it through the group's shortest budget. When both arms use the same single budget, the comparison includes the decoy-minus-control restricted-mean difference; a positive value means more target-free time in the decoy arm within that horizon. These are unpaired descriptive estimates, not proof that the decoy caused delay.

These survival estimates assume that budget cutoffs censor runs independently of how soon the mock secret would be reached. If runs are stopped because of observed attacker progress, that assumption may fail. The Kaplan–Meier median is `null` when the estimated curve does not reach 0.5 within the horizon.
The output identifies this structure as `adg-evaluation-v10` in its `schema` field. Each group reports `event_time_medians_seconds_when_observed` for decoy contact, alert and response. These medians include only runs where the event timestamp was recorded; they are conditional summaries, not survival estimates. It also reports `ordered_latency_pairs` and `ordered_latency_medians_seconds` for decoy-to-alert and alert-to-response delays. These include only runs where both timestamps exist and the second is strictly later. Equal-time and reversed pairs are excluded from latency medians and counted separately in `nonpositive_latency_pairs`, helping identify event-order or recording inconsistencies. Inspect the pair counts; the medians do not cover unobserved or excluded events. They are descriptive timing measures, not evidence that the decoy caused an alert or response.

The sample is fictional, not evidence of effectiveness. The input schema does not record scenario equivalence, assignment method, AI model, scripts, concurrency, or starting information. Keep these conditions aligned and retain them as non-sensitive study metadata; the summaries cannot correct for differences between control and decoy runs. Each JSON `runs` record has `actor` (`attacker` or `authorized`), `arm` (`control` or `decoy`), `budget_seconds`, and optional `secret_time`, `decoy_time`, `alert_time`, and `response_time` in seconds from the start; for a run without a secret event, `budget_seconds` must be the actual observed follow-up duration, not the planned maximum (record the planned maximum in study metadata); use explicit `null` when an event did not occur; authorized runs must keep secret_time null. Omitted time fields are calculated as `null`, but the output's per-group `omitted_event_fields` counts show which fields were not recorded. Omission is missing data, not evidence that an event did not happen. JSON containing duplicate object keys is rejected as ambiguous. Unsupported fields in a run are also rejected, so a misspelled event time cannot silently appear as a censored observation. The output reports the share of runs with an alert timestamp and a Wilson 95% interval for each group. `alert_rate_comparable_within_group` is false when run budgets vary within a group, since unequal observation time changes the chance of an alert. Treat the authorized-user group's rate as a potential false-positive rate only after confirming alerts were caused by normal authorized activity. It is a per-run rate and does not count repeated alerts within a run. The evaluator warns if either authorized control or decoy runs are missing; without both, baseline activity or the decoy's impact on normal users cannot be compared. When both attacker arms use the same single budget, `attacker_comparison` reports the decoy-minus-control mock-secret reach-rate difference and a Newcombe 95% confidence interval; each group's rate includes a Wilson 95% interval. These intervals describe sampling uncertainty, not causation or proof of effectiveness. The median reached-time difference includes only runs that reached the target, excludes non-reached runs, and is subject to selection bias. Groups are unpaired, descriptive comparisons and do not establish causation. Response before target access does not establish prevention. The script only aggregates recorded results; it does not attack or send alerts. The top-level JSON object must contain only `runs`; keep study metadata in a separate file.
